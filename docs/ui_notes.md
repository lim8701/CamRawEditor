# UI 노트 — 컨택트 시트 · 편집됨 배지 · 얼굴 부위 선택

> `CLAUDE.md` 에서 분리했다(그 파일은 매 세션 컨텍스트에 통째로 올라가므로 가볍게
> 유지한다). CLAUDE.md 에는 요약과 이 문서 포인터만 남아 있다.
>
> 셋 다 커뮤니티 UI 피드백에서 나왔고, **되돌린 시도와 그 이유**가 함께 적혀 있다.

- **컨택트 시트(빈 캔버스의 폴더 격자)** — "폴더를 골랐는데 가운데가 텅 비어 어색하다,
  사진이 나오고 그걸 누르면 바로 열렸으면"이라는 피드백. 사진을 안 연 상태의 캔버스에
  현재 폴더를 격자로 깐다. ⚠️**클릭=선택 / 더블클릭=열기**(탐색기 목록과 같은 규칙) —
  처음엔 '고르러 온 화면이니 한 번 클릭이면 된다'로 만들었다가 **되돌렸다**: 잘못 누르면
  2~4초 디코딩을 그대로 기다려야 한다는 보고.
  - ★**선택 상태는 격자가 따로 갖지 않는다** — `contactSheet.selectedPath` 는 좌측 탐색기의
    `fileListView.currentIndex` 에서 **파생**된다. 격자 클릭은 `selectInExplorer(path, false)`
    로 탐색기 선택을 옮기기만 하고, 탐색기에서 고르면 격자가 따라온다(+ 화면 밖이면 그 자리로
    스크롤). 진실원이 하나라 양방향 동기화를 맞출 코드가 없다 — 상태를 두 벌 두면 그때부터
    한쪽만 갱신되는 경로가 생긴다. focus=false 는 격자에서 방향키를 목록에 뺏기지 않으려는 것.
  - ⚠️**첫 사진 자동 로드는 하지 않는다** — '시작은 폴더만 연다'가 설계 결정이고(위 실행/환경),
    원하지도 않은 사진을 2~4초 디코딩하게 된다. 고를 수 있게 보여주기만 한다.
  - ★**격자는 상태가 아니라 모드**이고 **규칙은 두 줄뿐**이다(`win.gridPinned`): ①**G** 키 또는
    상단 경로 표시줄 오른쪽 **▦ 버튼**으로 켜고 끈다 ②아직 사진을 안 열었으면 켜져 있다.
    다른 사진을 열면(격자·탐색기·프리뷰 어디서든) 닫힌다 — `win` 의 `onImageChanged` **한 곳**이
    맡는다. ⚠️경로 비교 없이 `imageChanged` 만 보면 WB 커밋 같은 재디코딩에도 닫혀 '왜 꺼졌지'가
    된다(`_gridLastPath`).
  - ⚠️**조건을 늘리지 말 것.** '사진을 안 열었을 때만' → 되돌아갈 길이 없다는 보고 → G 모드 추가,
    거기에 '다른 폴더로 이동하면 자동으로 켜기'까지 붙였더니 **켜지고 꺼지는 상황이 경우마다 달라
    혼란스럽다**는 보고를 다시 받고 걷어냈다(폴더를 옮겨도 편집 중인 사진은 그대로 둔다).
  - ⚠️토글 버튼은 **창 크롬(경로 표시줄)** 에 둔다 — 캔버스 좌하단에 띄웠다가 **사진 위에 떠 있는
    게 어색하다**는 보고로 옮겼다. 탐색기 툴바(♥/⧉/☑) 옆은 통계 문구 폭 예산이 버튼 3개 기준이라
    넣지 않았다. 아이콘은 글리프가 아니라 **사각형 4개로 직접** 그린다(폰트에 없으면 두부가 뜬다).
  - ⚠️격자는 **불투명 배경**을 깔고(`#1a1a1a`), 덮고 있는 동안 **아래 사진에 대한 오버레이는
    감춘다** — 촬영정보(I)·AI 캡션 바·`Compare original` 버튼. 안 보이는 사진의 정보가 격자
    위에 뜨면 어느 사진 얘기인지 알 수 없다.
  - ⚠️디코딩 중(`controller.busy`)에는 감춘다 — 더블클릭 후 2~4초 격자가 그대로면 '눌렀는데
    아무 일도 안 난' 것처럼 보인다.
  - ★**썸네일 요청 크기 160 은 임의 값이 아니다.** `ThumbProvider._make_thumb` 은 160 이하면
    RAF 임베드 **EXIF 썸네일**(실측 **1.4ms/장**), 넘으면 임베드 풀 프리뷰 축소 디코딩
    (**73.9ms/장 — 50배**)으로 간다. 셀을 키우자는 요청이 오면 선캐시 등 그 비용을 감당할
    방법을 먼저 정할 것(96px 는 4.8ms 로 오히려 160 보다 느리다 — 160 은 EXIF 썸네일 원본
    크기라 축소가 없다).
  - 썸네일 칸은 **정사각 160**(cell 178×198) = 탐색기 **호버 피크와 같은 크기**(피크도
    `sourceSize.width: 160`). ⚠️예전엔 160×112(가로 기준)라 **세로 사진만 75px 폭으로
    쪼그라들어** "피크만큼 크게 해달라"는 보고가 나왔다 — 가로 사진은 그때도 피크와 같은
    크기였고 문제는 세로였다. 정사각이면 어느 방향이든 긴 변이 160 이고, 제공 크기(160)와
    표시 크기가 같아 확대가 없다(세로 EXIF 썸네일은 120×180 이라 오히려 축소).
  - 모델은 탐색기와 같은 `explorerFiles`(검색·좋아요 필터 그대로), 폴더 항목은 뺀다.
    GridView 라 보이는 셀만 요청한다(503장 폴더 확인).
  - ★**'썸네일/편집 이미지 크기를 다양하게' 요청은 이 격자로 갈음하고 현행 유지로 결정**
    (사용자 판단). 다시 제안하기 전에 아래 두 제약을 먼저 볼 것:
    ①**좌측 탐색기는 패널 폭이 260px 고정**이라 썸네일을 키우면 파일명 자리가 없어진다.
    ②**메인 캔버스 줌은 맞춤↔1:1(프록시 픽셀) 두 단계뿐인 것이 구조 때문**이다 — 파이프라인이
    프록시(≤2560) FBO 에서만 렌더하므로 1:1 을 넘기면 없는 화소를 늘리는 것이라 **흐려지고**,
    핀트 확인이라는 목적에 오히려 해롭다. 진짜로 열려면 확대 영역만 원본에서 다시 디코딩하는
    구조가 필요하다(큰 작업).

- **'편집됨' 표시는 파일명 색 + 썸네일 배지 둘 다**(`ui/EditedBadge.qml`). 예전에는 파일명
  앰버 색 하나뿐이었는데 **12px 글자의 색만으로는 안 보인다**는 피드백이 왔다(색각 이상이면
  사실상 안 보인다). 같은 화면의 좋아요(♥)·짝 JPEG(+JPG)은 이미 배지인데 편집 표시만 그
  언어를 안 쓰고 있었다. 도안은 **앱 아이콘 그대로**(타이틀바와 같은 소형 아트 = R + 홀 3개).
  `packaging/make_icon.py --badge` 가 `assets/icons/edited.png`(48px)로 굽는다 — **.ico/.icns 와
  같은 원본에서 나오므로 아이콘을 다시 만들면 이 명령도 같이 돌릴 것**. 탐색기 행과 컨택트 시트가
  `ui/EditedBadge.qml` 하나를 공유한다.
  ⚠️**도안을 두 번 갈아엎고 여기까지 왔다** — ①`FilmStrip` 스프로킷 홀 축소판: 이 크기에서 구멍
  3개가 가로로 놓여 **말줄임표(…)로 읽힌다** ②Edit 패널 아이콘(조정 슬라이더) 축소판: 뜻은 맞지만
  여전히 어색하다 → **앱 아이콘으로 확정**(사용자 지정). 새로 그리지 말 것. 그리고 배지 도안은
  **실제 크기(18px)에서** 무엇으로 읽히는지 먼저 볼 것 — 4배로 키우면 ①도 멀쩡해 보였다.
  ⚠️글리프(✎ 등)는 쓰지 않는다 — 폰트에 없으면 두부(□)가 뜨는데 확인할 방법이 없다(격자 토글
  아이콘을 사각형 4개로 직접 그린 것과 같은 이유).
  ⚠️크기는 **♥(font.pixelSize 14)와 같은 14px** — 한 모서리 안에서 크기가 다르면 따로 논다.
  ★**배지는 칸 모서리가 아니라 '사진이 실제로 그려진 사각형' 모서리에 붙인다**(편집 배지·♥ —
  격자·목록 양쪽). 칸 기준이면 가로 사진은 사진 위, 세로 사진은 사진 밖 빈 칸에 놓여 **같은
  배지가 사진마다 다르게 붙은 것처럼 보인다**(사용자 보고). `thumbImg.paintedWidth/Height` 로
  계산.
  ⚠️**단 +JPG 배지만 칸 좌하단에 남긴다.** 셋 다 사진 기준으로 붙였더니 84×56 칸의 세로
  사진(사진 폭 37px)에서 아래 줄의 +JPG(22px)와 ♥(14px)가 **겹쳤다**(사용자 보고). +JPG 를
  칸 좌하단에 두면 ♥ 가 사진 오른쪽 끝으로 와도 22px 이상 벌어진다(세로 1:3 극단에서도 안전).
  컨택트 시트는 배지가 2개뿐이라 이 문제가 없다.
  ⚠️**썸네일 로드 전에는 감춘다**(`EditedBadge.ready`, ♥ 는 `status === Image.Ready`) —
  `paintedWidth/Height` 가 로드 전엔 0 이라 배지가 **칸 한가운데**에 뜬다(사용자 보고).
  placeholder 위에 배지를 띄울 이유도 없다.

- **얼굴 부위 전체 선택/해제**(`win.setAllFaceParts`, Face 탭의 `FACE PARTS  All None`) — 부위가
  11개라 얼굴 전체를 잡으려면 11번 눌러야 한다는 피드백. ⚠️`toggleMaskKey` 를 11번 부르지 않는다
  (호출마다 재조합 디바운스가 돌고 '첫 부위' 기본 대상 로직이 매번 재평가된다) — 키 목록을 한 번에
  만들고 **한 번만** 커밋한다. ⚠️그래서 **규칙이 두 곳에 있다**: 첫 부위를 켤 때의 기본 대상
  (faceSelMemo → 없으면 가장 큰 얼굴)과 마지막 부위를 끌 때의 memo 백업. `toggleMaskKey` 와
  같아야 하고 한쪽만 고치면 얼굴 선택이 어긋난다.
  ⚠️아래 `Clear` 버튼은 대안이 아니다 — `resetSky` 는 **전 레이어 초기화**(마스크 + 로컬 조정
  슬라이더 전부)라 훨씬 센 동작이다. `None` 은 현재 레이어의 부위 체크만 푼다.
  참고: 얼굴 **선택**(어느 인물인가)의 `All` 은 `FACES n` 줄에 예전부터 있었다 — 얼굴이 2명
  이상일 때만 보인다(1명이면 고를 게 없다). 부위 쪽 `All` 과 뜻이 다르니 머리글로 구분한다.

## 컨택트 시트 썸네일 — 로드 순서와 요청 크기

### 위에서부터 채운다 (Qt 는 뒤에서부터 처리한다)

"격자에서 썸네일이 역순으로 로드된다" 는 보고. `ThumbProvider.requestImage` 를 감싸 요청 순서를
기록해 재현했다(505장 폴더, 창 1500×912):

```
수정 전  0, 14, 13, 12, 11, 10, 9, 8, 7, 6, 5, 4, 3, 2, 18, 17   증가 2 / 감소 16
수정 후  1, 0, 2, 4, 5, 6, 7, 8, 3, 9, 10, 11, 12, 13, 14, 15    증가 16 / 감소 2
```

원인은 우리 코드가 아니라 **Qt 의 이미지 작업 큐가 LIFO** 라는 점이다. delegate 는 index 순서로
만들어지는데 로더가 마지막 것부터 집는다.

고친 방식은 **앞 칸의 완료를 기다리는 게이트**다. 시트가 `loadedCount`(성공/실패 누적)와
`loadWindow`(동시 요청 수, 2)를 들고, 칸은 `slot < loadedCount + loadWindow` 일 때만 `source` 를
건다. `Image.onStatusChanged` 가 Ready/Error 양쪽에서 카운터를 올린다(실패한 칸에서 멈추면 안 된다).

- ⚠️**고정 지연으로는 안 된다.** 칸당 12ms 를 먼저 넣어 봤는데 한 장 디코딩이 그보다 훨씬 길어
  여러 칸이 동시에 큐에 쌓이고 그 안에서 다시 뒤집혔다(증가 15 / 감소 18 = 뒤섞임).
- ⚠️**절대 index 로 게이트를 걸면 교착이다.** GridView 는 보이는 칸만 만들므로, 스크롤해서
  아래쪽만 떠 있으면 앞 칸이 인스턴스화되지 않아 조건이 영원히 안 풀린다. 그래서 `slot` 은
  **화면의 첫 칸**(`indexAt`)을 기준으로 잰다. 스크롤하면 카운터를 0 으로 되돌려 그 자리에서
  다시 위에서부터 채운다.
- ⚠️요청 중에 칸이 파괴되면 완료 신호가 오지 않는다 → 700ms 워치독이 진척 없을 때 한 칸씩
  밀어 준다. 실측 요청 간격은 중간값 **73ms**(=디코딩 시간)라 평소에는 워치독이 아니라 완료
  신호가 게이트를 돌린다.
**좌측 탐색기 목록도 같은 게이트를 쓴다.** 그쪽도 역순이었다(증가 1 / 감소 13).

★**게이트에는 상태가 넷 얽혀 있다 — 리뷰에서 네 개가 한꺼번에 걸렸다. 손댈 때 같이 볼 것.**

- ⚠️**워치독에는 상한이 있어야 한다.** 처음엔 진척이 없으면 무조건 +1 이라, 다 뜬 뒤에도
  700ms마다 계속 올랐다(20초면 +28). 그러면 **다음 폴더에서 모든 칸이 한꺼번에 armed** 가 돼
  게이트가 없는 것과 같아진다 → `loadedCount < count − firstVisibleIndex` 동안만 돌린다.
- ⚠️**폴더(모델)가 바뀌면 카운터를 되돌려야 한다.** 리셋이 `onFirstVisibleIndexChanged` 에만
  있으면, 맨 위에 있는 채로 폴더를 바꿀 때 그 값이 안 변해 리셋이 **안 걸린다**(= 두 번째
  폴더부터 역순 채우기가 그대로 돌아온다). `onModelChanged` 에서도 리셋한다.
- ⚠️**`indexAt` 이 주는 -1 을 0 으로 접지 말 것.** 목록은 `spacing: 2` 라 행 사이에 아이템이
  없는 지점이 있고 거기서 -1 이 온다. `Math.max(0, …)` 로 접으면 한참 아래를 보고 있는데
  첫 칸이 0 이 되고, 같은 신호로 `loadedCount` 까지 0 이 돼 **보이는 행이 하나도 armed 가
  아니게 된다**(워치독이 700ms에 하나씩 기어올 때까지 빈 화면). 모르면 직전 값을 유지한다.
- ⚠️**한 번 뜬 그림은 계속 armed 로 둔다.** 스크롤 리셋이 `armed` 를 풀면 `source` 가 비워져
  이미 보고 있던 썸네일이 회색 자리표시자로 되돌아간다 — 66px 스크롤마다 반복이라 드래그
  내내 깜빡인다. 리셋은 **새 요청을 막는 것**이지 이미 받은 그림을 버리는 것이 아니다.
- ⚠️**폴더 행은 게이트 자리를 먹으면 안 된다**(좌측 목록만 해당). `main.py` 가 디렉터리를 목록
  맨 앞에 넣는데, 그 행들은 썸네일을 요청하지 않아 완료 신호도 없다. 그대로 세면 하위 폴더가
  D개인 폴더에서 첫 사진이 `slot = D` 라 워치독이 D번 밀어 줄 때까지 회색이다(D=10 → 약 7초).
  `slot` 기준을 `max(firstVisibleIndex, dirCount)` 로 잡는다.

### ★⚠️HiDPI 가 빠른 경로를 통째로 벗어나게 하고 있었다

`sourceSize` 는 **논리 픽셀**이라 Qt 가 devicePixelRatio 를 곱해 provider 에 넘긴다. 배율 125%
화면에서 실측 요청 크기가 **200**(=160×1.25) 이었고, `ThumbProvider._make_thumb` 의 분기가
`edge <= 160` 이라 **모든 칸이 느린 경로**(임베드 프리뷰 축소 디코딩)로 갔다 — 1.4ms 대 73.9ms,
**50배**다. 순서를 재다가 요청 간격 중간값이 73ms 인 것을 보고 알았다.

썸네일 요청을 `win.thumbPx(px)` 로 통과시켜 provider 가 항상 **160 device px 이하**를 받게 했다.
컨택트 시트·좌측 목록(96)·태그 패널(160) 세 곳이고, **호버 피크는 예외**다(아래).

`thumbPx` 는 `px / dpr` 이 아니라 **`min(px, floor(160 / dpr))`** 다. 두 가지를 같이 지켜야 한다:

- ★⚠️**`round` 로 나누면 되돌아오는 반올림이 상한을 넘는다.** DPR **1.5**(윈도우 150% — 가장
  흔한 HiDPI 설정)에서 `round(160/1.5) = 107` 이고 Qt 가 `qRound(107×1.5) = **161**` 로 넘겨
  **빠른 경로를 그대로 놓친다**. 실측(`_make_thumb`, X100V RAF): edge 160 → 107×160 **0.6ms** /
  edge 161 → 107×161 **43.5ms**(72배). `floor` 면 106 → 159 라 안전하다. 전 배율 검산:
  1.25 → 160 ✅ / **1.5 → 161 ❌(→ floor 로 159)** / 1.75 → 159 ✅ / 2.0 → 160 ✅ / 3.0 → 159 ✅.
- ⚠️**요청값을 무조건 DPR 로 나누지도 말 것.** 제약은 '160 device px' 이지 '항상 1/DPR' 이 아니다.
  나누기만 하면 DPR 2 에서 96 요청이 96 device px 로 도착하는데, 그 칸은 84×56 논리(=168×112
  device)라 가로 사진이 **1.75배 확대**된다. 상한 안에서는 요청값을 그대로 살린다.
- ★⚠️**"더 크게 요청해도 확대뿐" 은 사실이 아니다**(한동안 그렇게 적혀 있었다). `edge > 160`
  이면 provider 는 EXIF 썸네일을 확대하는 게 아니라 **임베드 프리뷰를 따로 축소 디코딩**해
  진짜 고해상도를 돌려준다(실측 edge 320 → 213×320, 43.7ms). 즉 이 상한은 **속도↔선명도 교환**
  이지 공짜가 아니다 — 수백 장을 그리는 격자·목록에서만 이득이 비용을 넘는다.
- ⚠️**호버 피크(`peekImg`)에는 상한을 걸지 않는다.** 팝업 크기가 이미지의 implicit 크기
  (= 받은 픽셀 / DPR)에 물려 있어(`width: peekImg.width + 8`) 요청을 줄이면 **팝업이 통째로
  작아진다**(DPR 2 에서 항목 폭 106 → 53 논리px = 반토막). 한 장짜리 호버라 느린 경로(43ms,
  캐시됨)를 타도 되고, 그래야 HiDPI 에서 선명도도 유지된다.
- 효과: 요청 간격 중간값 **73ms → 3ms**, 컨택트 시트 요청 크기 200 → 160, 목록 120 → 96.
- 그 덕에 순서도 완전히 정렬됐다 — 한 장이 3ms 라 게이트가 깔끔하게 직렬화된다:

```
컨택트 시트  0,1,2,…,15   증가 18 / 감소 0
좌측 목록    0,1,2,…,14   증가 14 / 감소 0
```

⚠️썸네일 요청 크기를 바꿀 일이 생기면 **반드시 `win.thumbPx()` 를 거칠 것**(호버 피크만 예외).
직접 숫자를 넣으면 배율이 큰 화면에서 조용히 50배 느린 경로로 돌아간다.
