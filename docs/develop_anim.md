# Develop 애니메이션 — RAW 에서 최종까지를 하나의 타임라인으로

RAW Peek(`R`) 의 다섯 번째 탭(`5`). 이 사진이 **센서 모자이크에서 최종 결과까지 어떤 순서로
무엇을 거쳤는지** 연속으로 재생한다. 재생·스크럽만 하고 **파일로 저장하지 않는다.**

RAW Peek 의 나머지 네 탭이 "디모자이크 **이전**"을 보여 준다면, 이 탭은 "디모자이크 **이후**"를
보여 준다. 두 개가 이어져 하나의 이야기가 된다.

- 코드: `develop_anim.py`(스케줄·값 계산, 단일 진실원) · `raw_peek.develop_mosaic`(모자이크 그림)
  · `main.Controller.develop*` · `ui/Main.qml` 의 `pipeAnim` · `ui/RawPeekWindow.qml` 의 Develop 탭
- 열기: `R` 또는 **우측 셀렉터 레일 하단의 `▩`**(단축키 `?` 위). 일반 이미지에서는
  감추지 않고 **회색으로 남긴다** — 사라지면 왜 없는지 알 수 없다.
  ⚠️`▦` 는 경로 표시줄의 컨택트 시트 토글이 이미 쓰고 있어 피했다.
- 조작: `5` 로 진입 · `Space` 재생/정지 · `←/→` 단계 이동 · 하단 바 드래그로 스크럽
- 하단 타임라인은 **`view` 와 같은 폭**이다 — 정보 패널(`I`)이 열리면 그만큼 줄어든다.
  창 전체 폭으로 두면 눈금이 그림 위 어디를 가리키는지 읽히지 않는다(사용자 보고).
- 캡션은 **[n / N] 칩 + 단계 이름(15px, 굵게) + 설명(12px, 줄바꿈 2줄)** 2단이다. 한 줄에
  몰아넣고 `elide` 하면 **설명이 잘려 "왜 이 순서인가" 가 사라진다** — 그게 이 화면의 요점이라
  잘림을 허용하지 않는다. 실측: 가장 긴 설명(Mist, 1줄 643.6px)도 창 폭 **408px** 이상이면
  2줄에 들어간다. `dev_ui_probe` 가 활성 단계마다 두 Text 의 `truncated` 를 읽어 확인한다.
- ★**캡션 문자열은 영어다**(`develop_anim.STAGES` 의 `label`/`note`). 사용자에게 보이는
  문자열이라 그렇게 정했다 — 주석·이 문서는 한글 그대로다.
- ⚠️오버레이 배경 `MouseArea` 에 **`hoverEnabled: true`** 가 있어야 한다. 없으면 오버레이
  아래 패널의 `HoverHandler` 가 계속 반응해 **ToolTip 이 오버레이 위로 떠오른다**(사용자 보고).
  툴팁은 `ui/Main.qml` 87곳에 흩어져 있어 개별로 막을 수 없다 — 이 한 줄이 전부를 막는
  지점이다(클릭을 흡수하는 것과 같은 이유).
- ⚠️오른쪽 퍼센트 텍스트는 **폭을 고정**한다(`TextMetrics` 로 "100%" 를 재서). 내용에
  맞춰 두면 "5%"→"100%" 로 글자가 늘 때마다 트랙 오른쪽 끝이 밀려 **재생 중에 트랙
  길이가 계속 변한다**(사용자 보고).

## 왜 셰이더 uniform 을 옮기는 방식인가

`adjust.frag` 의 현상 단계는 거의 전부 **이미 uniform 으로 노출**돼 있다. 그래서 "단계를 하나씩
켜는 애니메이션" = **uniform 을 중립값에서 실제값으로 천천히 옮기는 것**이고, 셰이더도
`pipeline.py` 도 건드릴 필요가 없다.

`pipeline.py` 로 단계를 재오케스트레이션하는 길은 **기각**했다. 순서·계수 조립이
`render_full`(약 470줄) 안에 있어 그걸 복제하는 것은 **export 정합을 복제**하는 짓이고, 어차피
numpy 로는 스크럽에 필요한 실시간이 안 나온다(26MP 그레인만 20.6s).

⚠️샘플러 한도는 문제가 아니었다. `adjust.frag` 는 16/16 을 쓰지만 그 한도는 **스테이지당**이라
**인스턴스를 하나 더 만들어도 새 샘플러가 0개**다(`pipeFull` 이 이미 그 증거).

## ★⚠️슬라이더를 애니메이션하면 안 된다

룩 파라미터는 `win.*` 이 아니라 **슬라이더 객체에서 직접** `pipe` 로 들어간다. 슬라이더 값을
건드리면 셋이 동시에 터진다:

1. `editSaveWatch`(약 70항목에 슬라이더 `.value` 가 직접 들어 있다) → `scheduleSave()` →
   **사이드카 저장 + undo 스택 push**
2. 개별 `onValueChanged` 가 파이썬을 부른다 — `setMistAmount` · `syncFilmSim` ·
   `wbTimer`(**RAW 재디코드**) · `mistFieldTimer` · `stampGrainTimer`
3. `histWatch` → 히스토그램 재계산

`win._applying` 가드는 2번의 일부를 못 막고, 장시간 true 로 두는 것 자체가 위험하다.

→ **스냅샷을 한 번 읽고, 그 뒤로는 `pipeAnim` 의 자체 프로퍼티에만 쓴다.** 편집 상태는
하나도 건드리지 않는다.

## 이음새는 한 줄

`pipeView.sourceItem` 이 전체 렌더를 갈아끼우는 유일한 지점이다:

```qml
sourceItem: win.morphOn && pipeAnimLoader.item ? pipeAnimLoader.item
                                               : (win.compareOn ? comparePipe : pipe)
```

크롭·줌·기하 변환은 전부 그 **하류**라 그대로 적용된다. `pipeAnim` 은 `gpuExportLoader` 와 같은
이유로 `Loader { active: win.morphOn }` 안에 있어 유휴 시 GPU 비용이 0 이다.

## ★⚠️`pipeAnim` 은 ★렌더 경로 4중 계약의 일부가 **아니다**

`adjust.frag` 를 쓰는 네 번째 인스턴스지만 **프리뷰 전용 장식**이고 export 에 아무 영향이 없다.
`pipeline.render_full` 과 동기화하려 들지 말 것 — 룩 파라미터를 새로 만들 때 여기까지 배선할
의무는 없다.

다만 uniform 을 **추가**하면 이름 집합이 갈라져 그 uniform 이 조용히 기본값(0)으로 남는다.
그래서 `python presets.py` 가 **`pipe` / `pipeFull` / `pipeAnim` 세 곳의 프로퍼티 이름 집합을
대조**한다(`fullScale` 만 GPU export 전용으로 허용). 일부러 하나를 빼서 검사기가 잡는 것을
확인했다.

## 애니메이션하지 않는 단계 — 없는 것과 안 보여주는 것은 다르다

| 단계 | 왜 |
|---|---|
| 디모자이크 | 다이얼이 아니다 → CFA 모자이크 그림과 **교차 페이드** 로 표현 |
| 렌즈 보정 | 디코드에 이미 적용(프록시가 보정된 상태) |
| 톤 커브 | 값이 아니라 **텍스처**(`curve` 샘플러)라 uniform 으로 못 섞는다 |
| 선형화 / 헤드룸 | 이미지 연산이 아니라 **표현 방식의 변환**이라 '적용 전' 상태가 의미를 갖지 않는다. 머리 구간의 Gray/CFA 그림을 감마 없이 선형으로 그린 것이 이 지점과 맞춘 것이다 |
| **하이라이트 디새추(`hlDesat`)** | **의도적으로 없음** — 아래 절의 측정 참조 |

→ 애니메이션은 "센서가 기록한 밝기(선형)" 에서 시작한다. 캡션이 이 사실을 말해 주어야 한다.

### ★프론트엔드 전수 대조 (auto exposure 이전에 빠진 것이 있는지)

`adjust.frag` main() 을 처음부터 훑어 **이미지를 실제로 바꾸는 연산**을 전부 뽑아 대조했다.

| 셰이더 | 연산 | 단계 |
|---|---|---|
| 17행 | `srgbToLinear(src) × PROXY_HEADROOM` | 없음(위 표) |
| 40행 | 미스트 산란 | `Mist` |
| 43행 | `cam *= vec3(wbR,wbG,wbB)` | `White balance (as shot)` + 앞 그룹 |
| 44행 | `applyCamMat` | `Colour matrix` |
| 44행 | `pow(2, exposure + simExpEV + autoExpEV + skyA*.x·skyM*)` | 앞 셋은 각자 단계, **마스크 노출은 아래 ⚠️** |
| 48행 | `mix(clamp, filmic, filmicMix)` | `Tone mapping` |
| 59~62행 | **하이라이트 디새추** | **없음** |

**hlDesat 을 넣지 않는 이유는 측정이다.** 표본 34장:

- **6장은 게이트가 아예 꺼져 있다** — 자동노출 게인이 프록시 헤드룸(4.0)을 넘으면
  `raw_loader.clip_level` 이 도달 불가능한 값을 돌려준다(후지에선 흔한 조건이다).
- 나머지 28장 중 **영향 화소가 0 이 아닌 것은 3장**, 최대가 0.31%(`DSCF1659`)다. 그 3장은
  변화량이 152~255코드로 크지만 면적이 극히 작다(부분 클립된 하이라이트 코어).

그런데 uniform 값은 RAW 에서 **항상 1.0** 이라, 단계로 넣으면 `active_stages` 가 늘 활성으로
보고 **거의 모든 사진에서 아무 일도 안 일어나는 구간**이 생긴다 — "티가 안 나니 합쳐라" 로
정리한 그 문제와 같다. 넣으려면 스냅샷에 "이 사진에서 영향 화소가 몇 %인가"를 미리 계산해
게이팅해야 한다(프록시에서 numpy 로 가능). **지금은 넣지 않기로 했다(사용자 결정).**

⚠️**마스크 노출(`skyA*.x`)만 위치가 어긋난다.** 셰이더는 그것을 44행 노출 지수 안에서 곱하는데,
skyA/B/C 15개를 `Colour & finishing`(필름시뮬 뒤)에 묶어 뒀다. 마스크의 나머지 성분은 실제로
9.7단계(199행)라 그쪽이 맞고 **노출 성분만** 프론트엔드다. 순서 검사가 통과하는 것은 대표 위치를
`max()` 로 재기 때문이다. 매 프레임이 실재하는 셰이더 상태이므로 틀린 그림은 아니지만, 마스크
노출이 큰 사진에서는 실제 적용 지점보다 늦게 드러난다 — 마스크를 한 단계로 묶은 결과다.

## filmic 은 셰이더에 손잡이를 넣어 보여준다

처음엔 보류했는데("연결성이 너무 떨어진다" 는 사용자 지적) `adjust.frag` 에 `filmicMix`
uniform 을 넣었다. `pipe`/`pipeFull` 은 **1.0 리터럴 고정**이라 프리뷰·GPU export 는 무영향이고
(`mix(x, y, 1.0)` 은 `y` 와 **비트 동일**하다), `pipeline.render_full`(CPU export)은 셰이더를
쓰지 않으니 손댈 것이 없다. 움직이는 것은 `pipeAnim` 뿐이다.

**'끄기' 끝점을 무엇으로 할지는 재서 정했다**(X100V `DSCF8035.RAF`, filmic 기준):

| 후보 | 평균 | filmic 과의 평균절대차 | \|Δ\|>2코드 픽셀 | 판정 |
|---|---|---|---|---|
| OETF 만(롤오프만 끄기) | 0.5019 | **0.0 코드** | **0.2%** | **기각 — 보이지 않는다** |
| 순수 선형(OETF 없음) | 0.2609 | **61.5 코드** | **95.4%** | 채택 (**+0.94EV**) |
| filmic(현재) | 0.5018 | — | — | 기준 |

⚠️롤오프만 끄는 방식은 단계를 보여줘도 **아무 일이 안 일어난다**(하이라이트 클립이 4.77%→0.32%
줄어드는 것뿐). 선형까지 내려가야 보인다.

→ 그래서 **머리 구간(Gray/CFA)도 감마를 걸지 않고 선형으로 그린다**
(`raw_peek.develop_mosaic`, 다른 RAW Peek 탭의 `_gamma8` 과 다르다). 밝은 모자이크에서 어두운
선형 렌더로 넘어가면 밝기가 튀어 연결이 끊긴다. 선형끼리 이어야 filmic 단계가 "선형 → 눈이 보는
밝기" 라는 제 몫을 한다. **머리 구간이 어두운 것은 버그가 아니라 센서 데이터가 원래 그렇다는
사실이다.**

## WB 도 손잡이가 이미 있었다 — 내가 잘못 읽었다

한동안 "디코드에 베이크돼 있어 못 보여준다"고 적어 뒀는데 **틀렸다.** 디코드가 굽는 것은
TREF(5500K 데이라이트) **기준까지**이고(`raw_loader._decode_native` 의 `user_wb=baked_wb(...)`),
그 사진의 실제 색온도는 셰이더의 `wbR/G/B` 가 상대 게인으로 올린다 — 즉 **평소에도 (1,1,1) 이
아니다.** 원인은 셰이더 주석이었다: `float wbR; // WB 프리뷰 게인 (커밋되면 1)`. 그 문장을 믿고
문서에 옮겨 적었다. 지금은 주석도 고쳤다.

실측 상대 게인(TREF 대비, green 정규화): 4825K → 1.039:1:1.246(편차 24.6%) /
4875K → 0.956:1:1.128(12.8%) / 5325K → 1.021:1:1.065(6.5%) / 4275K → 0.801:1:1.170(19.9%).

**두 조각으로 나눠 보여준다** — 자동노출/노출을 나눈 것과 같은 구분이다(카메라가 한 것 / 내가 한 것):

- `wb` **White balance (as shot)** — (1,1,1) → 카메라가 읽은 색온도. 독립 단계다.
- 내가 만진 Temp/Tint — **필름시뮬 앞 그룹**(`Temp, tone & detail`)에서 노출·NR·텍스처 등과
  함께 움직인다(사용자 결정). 셰이더가 WB 곱셈을 필름시뮬보다 앞에서 하므로 '앞 그룹'이 맞다.

⚠️중립은 (1,1,1) = 구운 TREF 그대로다. **"WB 를 아예 안 건 상태" 는 이 렌더 경로가 만들 수 없다**
— 절대 색온도를 정확히 하려고 디코드가 항상 기준을 하나 굽는다. 캡션이 그렇게 말해야 한다.
촬영 색온도가 5500K 근처면 중립과 같아져 단계가 자동으로 빠진다.

### 한 uniform 이 두 단계에 걸리게 하는 방법 (`_spans`)

WB 는 셰이더에서 곱셈 **한 번**이라, 두 단계로 보여주려면 단계마다 끝값을 따로 줘야 한다.
`_spans(snap)` 이 STAGES 순서대로 `{uniform: (시작, 끝)}` 을 만들고, 끝값은 기본이 스냅샷의
최종값이며 `end={"wbR": "_wbAsShotR", ...}` 로 다른 스냅샷 키를 지정할 수 있다.

⚠️**누적값으로 이어가야 한다.** 처음엔 단계의 선언된 시작값을 그대로 lerp 했는데, 아직 시작하지
않은 뒤 단계(w=0)가 자기 시작값으로 앞 단계의 진행 결과를 **덮어썼다** — t=0 에서 WB 가 이미
as-shot 이 되는 버그였다. `run[u] = _lerp(run.get(u, a), b, w)` 로 고쳤다.

⚠️`active_stages` 도 사슬을 봐야 한다 — 중립 대비가 아니라 **그 단계 안의 (시작, 끝)** 이
움직이는지로 판정한다. 그래서 as-shot 그대로인 사진에서는 앞 그룹 안의 WB 가 아무 일도 하지 않고,
그 그룹은 다른 보정이 있으면 그것 때문에만 활성이 된다.

⚠️**사이드카는 WB 를 `kelvin` 이 아니라 `temp`/`tint` 키로 저장한다.** 없는 키를 읽어 as-shot 으로
폴백하는 바람에 "네 사진 모두 as-shot" 이라고 한 번 잘못 보고했다. 제대로 재니 사이드카 267개 중
**28.5%(76개)가 as-shot 이 아니고**, 그쪽 채널 게인 변화가 중간값 **14.1%**, 최대 40.1%
(5% 넘는 것 66개)였다. 나눌 값이 있다는 판단의 근거가 이것이다.

## ★중립값이 0 인 uniform 만 있는 게 아니다

`develop_anim.neutral()` 이 단일 진실원이다. 0 이 아닌 것들:

| uniform | 중립 | 왜 |
|---|---|---|
| `camM0/4/8` | **1.0** | 3×3 매트릭스의 대각 — 항등이 1 |
| `contrast` | **1.0** | 곱셈자 |
| `skyB*.w`(skyContrast) | **1.0** | ★전역 `contrast` 와 같은 곱셈자다. 0 으로 두면 마스크 안쪽 대비가 무너진다 — **검증에서 잡힌 실제 버그** |
| `skyC*.z/.w`(invert, hasMask) | **실제 값 유지** | 조정이 아니라 설정·게이트다. 0 으로 만들면 레이어가 꺼져 **팝** 이 생긴다 |
| `autoExpEV` | **−autoEV** | 자동노출은 디코드에 이미 곱해져 있고 이 uniform 은 원래 '끄기' 오프셋이다. −autoEV → 0 으로 옮기면 자동노출이 걸리는 과정이 그대로 보인다 |

⚠️`LOOK_DEFAULTS` 를 그대로 중립으로 쓰면 안 된다. `mistRadius 1.0` · `mistHi 0.8` ·
`grainSize 0.5` · `sharpenRadius 1.0` 같은 **'모양' 파라미터**는 짝이 되는 강도가 0 이라서
중립인 값이다. 강도가 0 이 아닌 상태에서 이 값들을 보간하면 **중립화가 아니라 룩이 바뀐다.**
→ 애니메이션 대상은 **강도(amount) uniform 54개**뿐이고 모양 파라미터는 실제 값에 고정한다.

## 스케줄

`STAGES` 22개가 `adjust.frag` main() 의 번호 순서와 같다. 머리는 네 단계다:

| 단계 | 무엇이 바뀌나 |
|---|---|
| **Sensor readout** | Gray 그림 — 픽셀마다 밝기 하나뿐. 선형이라 어둡다 (**박스 평균** = Gray 탭과 같은 그림) |
| **Colour filter array** | Gray 가 걷히고 CFA 색이 드러난다(X-Trans 6×6 / 베이어 2×2) |
| **Demosaic** | CFA 그림이 걷히고 셰이더의 디모자이크 결과가 드러난다 |
| **Tone mapping** | `filmicMix` 0→1 — 여기서 그림이 밝아진다 |

앞 세 단계는 uniform 이 없다. 파이썬이 그린 그림 두 장(Gray/CFA)을 셰이더 렌더 **위에** 쌓아
놓고 위에 있는 것부터 차례로 걷어낸다 — `values()` 가 `gray`/`mosaic` 두 불투명도를 돌려준다.

**순서의 기준은 `shaders/adjust.frag` main() 의 실제 실행 순서다** — 주석의 번호가 아니다.
번호는 실행 순서와 다르다(미스트는 `1)` 인데 `0)` 프론트엔드보다 앞에서 돌고, 하이라이트
디새추는 `0.5)` 인데 톤 앞이다). `python develop_anim.py` 가 셰이더에서 각 단계 대표 uniform 의
등장 위치를 찾아 이 목록의 순서와 대조한다.

#### 미스트가 노출보다 앞인 것은 사실이다 (두 번 확인했다)

미스트를 노출 **뒤**에 적어 뒀다가 "auto exposure 이후부터는 개연성이 없어 보인다" 는 지적을
받고 고쳤다. 그런데 고친 뒤에도 "미스트가 노출보다 앞이라고? 이게 더 어색해 보인다" 는 반응이
왔다 — 어색하지만 **코드가 그렇다.** 주석이 아니라 배선으로 두 경로를 다 확인했다:

```glsl
// shaders/adjust.frag main()
vec3 cam = srgbToLinear(texture(src, uv).rgb) * PROXY_HEADROOM;   // 카메라네이티브 scene-linear
if (ubuf.mistAmt > 0.0 && ...) { ... cam = (1.0 - mk) * cam + mk * sc; }   // ← 미스트
cam *= vec3(ubuf.wbR, ubuf.wbG, ubuf.wbB);                                 // ← WB
vec3 lin = applyCamMat(cam) * pow(2.0, ubuf.exposure + ubuf.simExpEV + ...); // ← 매트릭스·노출
```

```python
# pipeline.render_full (CPU export) — 같은 순서
if _mist_amt > 0.0:
    nat = mist.apply(nat, ...)                                    # nat = 카메라네이티브
_base_exp = float(p.get("exposure", 0.0)) + _sim_ev + _auto_off   # ← 노출은 그 뒤
disp = wb.filmic(linsrgb)
```

**왜 그렇게 설계했나**: 산란 필드를 카메라네이티브에서 계산하면 필드가 **슬라이더와 무관**해져
한 번 구워 두고 uniform 하나만 섞을 수 있다 → 프리뷰가 실시간이 된다(`CLAUDE.md` 의 `mist.py`
항목). 그래서 캡션이 그 이유를 말해 주도록 note 를 바꿨다 — **어색함을 정보로 바꾸는 게
이 기능의 목적이다.** 순서를 눈으로 확인하려고 만든 화면이 실제로 그 일을 했다.

⚠️note 가 길면 캡션이 `elide` 로 잘려 이유가 사라진다. 가장 긴 note(미스트, Consolas 12px 에서
**467px**)도 창 폭 **491px** 이상이면 안 잘린다 — `dev_ui_probe` 가 활성 단계마다 캡션 Text 의
`truncated` 를 읽어 확인한다.

⚠️대표 위치는 **첫 등장 중 가장 늦은 것**으로 잰다. 일부 uniform 은 자기 단계보다 앞에서 한 번
쓰인다(`simExpEV` 는 노출 지수 안, `skyA0.x` 는 마스크 노출 합산) — 첫 등장만 보면 filmsim 이
노출 위치로, masks 가 맨 앞으로 잡힌다(실제로 그렇게 나왔다). main() 밖 헬퍼에서 소비되는
단계(`matrix`·`hsl`)는 **호출 지점**으로 잰다.

예외는 `filmic` 하나다(`_ORDER_EXEMPT`) — 표시 변환이라 셰이더에서는 노출 뒤인데, 거기서
보여주면 앞의 네 단계가 전부 캄캄한 선형 화면이 된다. 디모자이크 직후로 끌어올렸고 그 지점의
상태도 실재하는 셰이더 상태다(filmicMix=1, camM 항등, autoExpEV=−autoEV).

**파라미터가 중립과 같은 단계는 건너뛴다** — 그 사진에서 실제로 일어난 일만 보여 준다(스킵된
단계는 눈금을 그리지 않는다 — `marks()` 가 `active=False` + t=-1 로 돌려주고 읽는 쪽이 거른다.
⚠️한때 "흐리게 표시" 로 적어 뒀지만 구현되지 않았고, 걸러내지 않으면 눈금이 트랙 왼쪽
밖에 쌓인다). 활성 단계는 **균등 배분**이고 단계 안 보간은 `smoothstep` 이다.

**auto exposure 이후는 세 덩이다.** 처음엔 셰이더 단계를 거의 1:1 로 나열했는데, 전체 프레임
축소본에서는 각자 티가 안 나 빈 구간처럼 느껴졌다("거의 티가 안 나니 하나의 스텝으로 합칠 것"
→ 네 개 병합 → 다시 "auto exposure 이후 스텝에 대해서 정리가 필요"). 최종 구조는 **필름 룩을
기준으로 전 / 룩 / 후**다:

| 단계 | 담는 uniform |
|---|---|
| `predev` **Temp, tone & detail** | **wbR/wbG/wbB(내가 만진 만큼)** · exposure · highlights/shadows/whites/blacks · lumaNR/colorNR · texAmt · clarity · sharpenAmt · dehaze |
| `filmsim` **Film simulation** | lutStrength · simExpEV |
| `finish` **Colour & finishing** | saturation/vibrance · hslH/S/L · contrast · cgSat* · skyA/B/C*(마스크) · vignette |
| `grain` **Film grain** | grainAmt |
| `stamp` **Date stamp** | (uniform 없음 — 오버레이 불투명도) |

⚠️uniform 이 여러 셰이더 위치에 걸치지만 **덩이끼리는 겹치지 않는다**(전 ≤137줄 < filmsim 149 <
후 ≤208 < grain 219) → 순서 검사가 그대로 성립하고 예외가 필요 없다. 예전 `fine` 병합은
노출(44)부터 디헤이즈(137)까지만 묶어 그 사이의 tone/texture/clarity 와 얽혀 예외였는데,
경계를 필름 룩에 맞추자 그 예외가 사라졌다. 지금 예외는 `filmic` 하나뿐이다.

**uniform 커버리지는 검사로 지킨다**: 54개가 **중복 없이** 정확히 한 번씩 들어간다
(`len(ANIM) == len(set(ANIM))`, `dev_wiring_test` 가 t=0 중립 54/54 · t=1 실제값 54/54 로 확인).

**`stamp` 는 `grain` 뒤다.** 프리뷰에서 스탬프 오버레이가 셰이더 위에 얹히므로 화면과 맞는
순서다. ⚠️export 는 그레인이 스탬프에도 얹힌다(`docs/date_stamp.md` 의 "프리뷰와 export 의
합성식이 다르다") — 이 탭은 프리뷰 쪽을 따른다.
- 날짜 스탬프는 셰이더가 아니라 **QML 오버레이**(`stampOverlay`)라 uniform 이 없고 **불투명도로
  페이드인**한다. 그래서 처음엔 Develop 탭에 **아예 안 보였다**(사용자 보고) — `devShader` 는
  `pipeAnim` 만 그리기 때문이다. 그 사진에 스탬프가 없으면 단계 자체가 빠진다
  (`morphSnapshot` 의 `_hasStamp`).
  ⚠️지오메트리 식의 진실원은 `stampOverlay` 다 — 기준 사각형만 `devFrame` 으로 바꿔 같은 비율을
  다시 쓴다. ⚠️Develop 은 **크롭 전 전체 프레임**이라 크롭이 걸린 사진에서는 메인 프리뷰와
  스탬프 위치가 다르다(뷰가 다른 것이지 값이 틀린 게 아니다).

⚠️예전엔 교차 페이드 구간에 가중치를 더 주고(`1.4`) 앞뒤에 정지 구간(`HOLD_HEAD 0.6` /
`HOLD_TAIL 1.2`)까지 뒀는데, **첫 단계가 유독 길게 느껴졌다**(사용자 보고). 앞 정지 구간의
캡션이 첫 단계 이름이라 체감 길이가 두 배였던 것이다 — 가중치와 정지 구간을 전부 걷어냈다.
끝의 정지도 필요 없다: 재생은 t=1 에서 멈춰 그대로 머문다.

실측(X100V `DSCF8035.RAF`): 22단계 중 **활성 7개** — Sensor readout / Colour filter array /
Demosaic / Tone mapping / Colour matrix / Auto exposure / Film simulation. 거의 편집하지 않은
사진이라 이 정도가 정상이다.

## 함정 (전부 검증에서 잡혔다)

### ★⚠️파이썬에서 온 리스트는 QML 에서 `Array.isArray()` 가 **false** 다

`QVariantList` 라서다. 그걸로 vec4 를 판정했다가
`Error: Cannot assign QVariantList to QVector4D` 로 **`applyValues` 루프 전체가 중단**됐고,
뒤쪽 uniform 은 물론 **캡션까지 통째로 안 들어갔다**(`devLabel=""`). `length === 4` 로 판정한다.

교훈이 하나 더 있다: **표시 상태를 uniform 대입보다 먼저 세운다.** 그러면 값 대입에서 예외가
나도 캡션·타임라인은 살아 있어 증상이 한 곳에 묶이지 않는다.

### ★⚠️핸들러 안에서 파생 프로퍼티를 읽으면 갱신 전 값이 온다

`onModeChanged` 에서 `isDevelop`(= `mode === 4` 바인딩)을 읽었더니 **직전 값**이 와서
애니메이션이 탭에 **들어갈 때가 아니라 나갈 때** 시작됐다. 핸들러에서는 `mode === 4` 를
직접 본다. (`CLAUDE.md` 의 `simCombo` 사례와 같은 함정 — 두 번째다)

### ★⚠️모자이크 그림은 **센서 공간**, 셰이더 렌더는 **프록시 공간**이다

세로 사진에서 뒤가 비쳐 보이는 원인이 이것이었다. `raw_peek` 은 `raw_image_visible` 을 쓰므로
**회전 전** 센서 공간(가로 6246×4170)이고, 프록시는 rawpy(LibRaw)가 flip 을 적용한 세로
1709×2560 이다. 가로 그림이 세로 뷰 안에서 `PreserveAspectFit` 로 레터박스되면 위아래 띠가
**투명**하게 남고, 그 틈으로 아래의 (이미 현상된) 셰이더 렌더가 비친다 — "뒷 배경이 겹쳐 보여
시각화가 애매하다".

`develop_mosaic` 이 프록시와 같은 방향으로 돌린다. **flip→회전 매핑은 추측하지 않고 실측했다**:
모자이크 gray 를 네 방향으로 돌려 프록시 휘도와 상관계수를 재 가장 높은 것을 골랐다.

| flip | 회전 | 상관계수 | 샘플 |
|---|---|---|---|
| 0 | 없음 | +0.841 | Nikon D90 (NEF) |
| 3 | 180° | +0.793 | LG Nexus 5X (DNG) |
| 5 | 90° CCW | +0.838 / +0.872 | X-T5 · X100V (RAF) — 반대 방향은 **−0.271** |
| 6 | 90° CW | *샘플 없음* | dcraw 대칭으로 둔 값(모르는 코드는 회전 없음) |

회전 후 비율 오차는 세 flip 모두 **0.13% 이내**라 `Image.Stretch` 로 프레임을 채워도 안전하다.

거기에 더해 그림 쪽 크기를 **축마다 따로** `Math.min(implicit, parent)` 로 잡고 있었다 — 상자
비율이 그림 비율과 달라져 회전이 없는 사진에서도 레터박스가 생긴다. 지금은 프레임 `Item`
하나를 프록시 비율로 맞춰 두고 세 레이어를 `anchors.fill` 로 채우고, 그 아래 **불투명한 검정
바닥**을 깐다.

⚠️두 그림 레이어는 `smooth: false` 다. 파이썬이 **nearest** 로 축소해 남긴 CFA 반점이 요점인데
보간을 켜면 반점이 평균돼 그냥 사진처럼 보인다.

### `values()` 는 **모든** 단계의 uniform 을 먼저 실제값으로 채운다

스킵된 단계(중립==실제)의 값이 dict 에서 빠지면 `pipeAnim` 의 그 프로퍼티가 기본값 0 으로
남아 `contrast`(1 이어야) 와 `skyC*`(invert/hasMask) 가 틀어진다.

### ★"센서는 격자다" 는 **선으로** 보여준다 — 값의 반점으로는 안 읽힌다

Gray 단계에서 격자가 구분돼야 한다는 요구를 두 번 빗맞혔다. 전체 프레임을 nearest 로 줄이면
R/G/B 우물의 값 차이가 그대로 남는데, 그 뽑는 규칙을 어떻게 바꿔도 답이 아니었다:

| 위상 규칙 | 초록 표본 공간 자기상관(최악) | 결과 |
|---|---|---|
| stride = f (지터 없음) | — | 표본이 전부 같은 위상 → **화면이 전부 초록**(G 55.6% 인데 사실상 100%) |
| 행·열 1차 램프 | **1.000** | 완전 주기적 → **"조악한 격자 무늬"** |
| 2D 선형 | 0.494 | 평면이라 대각선 줄이 남는다 |
| XOR 해시 | **0.011** | 무늬는 없지만 **"오히려 더 이상함"** — 그냥 모래알로 보인다 |

문제는 무늬가 아니라 **매체**였다. 후보 도판을 뽑아 나란히 보고 정했다:

| 후보 | 인접 \|차분\| (가로/세로) | 판정 |
|---|---|---|
| A 박스 평균 | 1.44 / 1.63 | 깨끗하지만 **격자가 안 보인다** |
| B XOR 해시 nearest | 8.71 / 8.64 | 노이즈로 보인다 |
| **C 박스 평균 + 격자선** | 5.91 / 5.97 | **채택** |
| D 패턴 유닛 블록 + 격자선 | 5.71 / 5.81 | 격자는 보이지만 사진이 뭉개진다 |

- **Gray = 박스 평균**(깨끗한 값) + **격자선**.
- **CFA = nearest 표본** + **같은 격자선**. 색 반점이 요점이라 여기선 nearest 가 맞다.
- 선 간격은 `GRID_PX`(8) — **표시 픽셀 단위의 가독성 값이고 CFA 패턴 유닛이 아니다.**
  전체 프레임 축소본에서 출력 1px 은 광전자 우물 f개(실측 f=7~12)라 패턴 유닛(X-Trans 6,
  베이어 2)은 **1px 도 안 된다** — 격자로 그릴 수 있는 크기가 아니다. (예전 문서에 "패턴 유닛
  경계" 라고 적었던 것은 틀렸다.)
- ★★**그림 크기를 요청 크기와 정확히 맞춰야 한다.** `ny x nx` 는 축소배율 `f` 의 정수
  나눗셈이라 요청과 몇 px 어긋나는데(실측 595x892 vs 600x900), 그러면 QML 이 1.009 배로 늘려
  그리고 **1px 격자선이 어떤 곳은 2px, 어떤 곳은 사라진다** — 세로 사진에서 선 굵기가
  들쭉날쭉하다는 사용자 보고의 원인이었다. nearest 로 정확한 크기까지 리샘플한 **뒤** 격자선을
  그린다. 실측(격자 위상별 열 평균): 위상0 **12.7** vs 나머지 8개 평균 **28.0**, 나머지 편차
  **0.14** — 정확히 8px마다 1px이다. `dev_ui_probe` 가 `sourceSize == 표시 크기`(1:1)를 확인한다.
- 디모자이크 단계에서 두 그림이 걷히면 **격자도 함께 사라진다** — 그게 디모자이크가 하는 일이다.

⚠️CFA 단계가 Gray 보다 어두운 것은 정상이다(실측 평균 코드 30 → 14). 각 픽셀이 필터 하나를
통과한 빛만 기록하므로 표시 에너지가 1/3 가량이고, 디모자이크가 나머지를 채우면 돌아온다.
X-Trans 는 G 가 55.6% 라 CFA 단계가 유독 초록으로 보인다 — 센서가 그렇다.

### 머리 프레임의 밝기 — 표시 게인 체크박스를 따른다

머리 프레임은 원래 표시 게인을 **곱하지 않았다**. 셰이더의 t=0 은 `norm`(센서값을 포화로
정규화한 값)이라 게인을 곱하면 이음새에서 그림이 툭 어두워졌기 때문이고, 사용자의 요청도
"눈에 보이는 것보다 센서로부터 지금까지 변화되는 과정" 이었다.

그 뒤 Gray/CFA/Planes/Demosaic 에 `Display gain` 체크박스가 생기면서 **머리도 같이 따르게**
했다(사용자 요청). 실측(DSCF2354, 머리 프레임 평균 코드):

| | Gray 머리 | CFA 머리 | 셰이더 t=0 |
|---|---|---|---|
| 게인 끔 | 20.5 | 14.5 | 17.8 |
| 게인 켬 | 68.0 | 36.7 | 17.8 |

- ⚠️**이음새는 게인을 끈 상태에서만 매끄럽다**(평균 2.7코드 차이). 켜면 48.8코드로 벌어진다 —
  이음새를 재는 검증은 반드시 끈 상태로 할 것.
- 체크박스 기본값은 **켜짐**이라(다른 네 탭의 기존 동작 보존) Develop 도 기본이 밝은 머리다.
  '과정 그대로' 를 보려면 체크를 끈다.
- ★**기본값을 끔으로 바꾸자는 안은 사용자가 기각했다**(체크박스 하나가 다섯 탭을 똑같이
  지배하는 단순함을 택함). 이음새가 기본으로 벌어지는 것은 **알고 받아들인 것**이니,
  "Develop 은 기본이 정직해야 한다" 며 되돌리지 말 것.
- 카페 게시글 도판(`develop_post/frames/`)은 게인 **끈** 상태로 뽑혀 있다 — 그게 이음새가
  매끄러운 쪽이라서다. 도판을 다시 뽑을 때도 끈 상태로.

### ★★생성 스크립트가 **두 줄 바인딩**을 반토막 냈다 — 빨간 마스크가 그대로 나왔다

마스크가 있는 사진의 Develop 탭에 **빨간 마스크 오버레이가 보였다**(사용자 보고). `pipeAnim` 의
선언은 분명히 `property real skyShowLayer: -1.0` 였는데 런타임 값은 **0.0** 이었다.

원인: `pipe` 의 이 바인딩이 두 줄이다.

```qml
property real skyShowLayer: (win.showSkyMask && win.activePanel === 2)
                            ? win.activeLayer : -1.0
```

`pipeAnim` 을 생성하는 스크립트가 **줄 단위**로 돌면서 첫 줄만 `-1.0` 으로 치환하고 둘째 줄을
그대로 남겼다:

```qml
property real skyShowLayer: -1.0
                            ? win.activeLayer : -1.0     // ← 고아. -1.0 은 truthy → 레이어 0
```

**QML 경고가 하나도 안 났다** — 문법적으로 완전한 삼항식이니까. `presets.py` 의 이름 집합
대조도 못 잡는다(이름은 맞다).

→ `dev_wiring_test` 가 이제 `skyShowLayer`/`clipWarn`/`zoneShow` 의 **평가된 값**을 읽어
확인한다. 선언 텍스트를 보는 검사로는 이 종류를 절대 못 잡는다. 블록 전체를 훑어 이어지는
줄이 남았는지도 확인했다(`pipeAnim` 에 하나 더 있었지만 그건 의도한 `grainShape` 의 두 줄).

### 로드가 끝나기 전에 Develop 으로 옮기면 아무 일도 안 일어났다

`devBegin()` 은 `controller.rawPeekOpened` 가 false 면 그냥 빠져나간다. "reading sensor data"
중에 `5` 를 누르면 그대로 끝이었고 **다시 시도하지 않았다**(사용자 보고).

→ 준비 완료를 감지하는 `Connections`(`onRawPeekChanged` 의 false→true 전이)에서 그때 모드가
Develop 이면 `devBegin()` 을 다시 부른다. `dev_early_probe` 가 **기다리지 않고 곧바로**
`mode=4` 로 옮겨 재현하고(실측 그 순간 `rawPeekOpened=False, rawPeekBusy=True`), 로드 후
`morphOn`·`developReady`·`pipeAnim`·단계 목록이 모두 서는지 확인한다. 수정을 일부러 지우면
세 항목이 전부 실패하는 것도 확인했다.

### ★`rawPeekAvailable` 바인딩이 **한 장 뒤처져** 있었다

레일 아이콘을 붙이면서 드러난 **선재 버그**다. `rawPeekAvailable` 의 notify 가 `imageChanged`
였는데, 그 시그널은 프록시를 올리는 시점에 나가고 **`_ui_path` 갱신 뒤에는 아무 시그널이 없다.**
게터는 `self._ui_path or self._path` 를 보므로 바인딩이 **이전 사진**의 값에 멈춘다:

- RAW → JPG 로 옮겨도 아이콘이 켜진 채 (그리고 **`R` 단축키도 살아 있었다**)
- JPG → RAW 로 옮겨도 꺼진 채

→ 전용 시그널 `rawPeekAvailChanged` 를 만들어 `_ui_path = self._path` **직후**에 쏜다.

⚠️**컨트롤러 게터를 직접 부르는 검증은 이걸 못 잡는다** — 게터는 처음부터 옳았고,
`peek_wiring_test` 는 `c.rawPeekAvailable` 을 읽어 `False OK` 를 찍고 있었다. 레일 아이콘의
**아이템 상태**(`MouseArea.enabled`, Label 색)를 읽는 `rail_icon_probe` 에서 잡혔다.
[[verify-the-real-path]] 의 같은 교훈이 QML 바인딩 쪽에서 다시 나온 것이다.

### ★`Shortcut{}` 은 전체화면 오버레이의 `Keys` 핸들러보다 **먼저** 잡는다

RAW Peek 이 떠 있는데 **`Enter` 를 누르면 프리뷰가 열렸다**(사용자 보고). `Shortcut` 은 앱
전역이라 오버레이가 포커스를 갖고 있어도 먼저 발동한다.

`ui/Main.qml` 은 이걸 알고 `_keysBlocked`(= `_typing || rawPeekWin.visible`)를 두고 파일 머리에
"새 단축키는 `_typing` 이 아니라 **`_keysBlocked`** 를 가드로 쓸 것" 이라고 적어 뒀는데, RAW Peek
보다 오래된 선언 두 개가 개별 조건만 보고 있었다:

| 위치 | 시퀀스 | 원래 조건 |
|---|---|---|
| Main.qml | `Return` / `Enter` | `showExplorer && currentIndex>=0 && !previewWin.visible && …` |
| Main.qml | `Alt+Up` | `!batchActive && !wallActive && !previewWin.visible` |

둘 다 `!win._keysBlocked` 를 앞에 붙였다. 예외는 **`R` 하나**다 — 토글이라 오버레이가 떠 있을
때도 살아 있어야 닫힌다.

→ `python shortcuts.py` 가 이제 `Shortcut{}` 27개를 전수 확인한다(`guard_report`).
⚠️검사는 **주석을 걷어낸 뒤** 봐야 한다 — 주석에 든 `_keysBlocked` 를 세다가 `R` 예외까지
통과시켜 검사가 헛돌았다. 가드를 일부러 지워 잡히는 것을 확인했다.

### 그레인 원판은 **움직이는 중에는 끈다**

"grain 이 포함되면 느려진다" 는 보고. 원인은 `Round grains`(원판 원시체)다:

- 원판은 샘플당 해시가 **1 → 27 개**로 늘고(3×3 이웃 합산) 그것을 **3층 × 3옥타브**로 돈다.
  CPU export 실측으로는 사각 셀 대비 **11~12배**(26MP 20.6s → 258s, 병렬 5.8s → 64s).
- 정지 화면이면 한 번만 그리니 티가 안 나지만, 애니메이션은 **16ms마다** 다시 그린다.
- 파이썬 쪽은 무죄다 — `develop_anim.values()` 가 **0.111 ms/호출**(프레임 예산의 0.7%).
- 셰이더에 `if (ubuf.grainAmt > 0.0)` 조기 이탈이 있으므로 이 비용은 **Grain 단계부터만** 든다.

→ `pipeAnim.grainShape` 를 `grainShapeCheck.checked && !rawPeekWin.devMoving` 으로 물렸다.
`pipe` 가 슬라이더 드래그 중에 하는 것과 **같은 정책**이다(드래그=빠른 근사, 릴리즈=정확).
`devMoving` = 재생 중이거나 타임라인을 드래그하는 중. 멈추면 정확한 모양으로 돌아온다.

검증(실행 중인 UI 에서 아이템 상태를 직접 읽음, 체크박스를 켜고):

| devPlaying | devMoving | `pipeAnim.grainShape` |
|---|---|---|
| true | true | **0.0** (사각 셀) |
| false | false | **1.0** (원판) |

⚠️체크박스를 건드리면 사이드카가 저장되므로 이 검증은 **스크래치패드에 복사한 사진**으로만
돌린다.

### 모자이크 그림이 전부 초록이었다

`develop_mosaic` 의 다운샘플 stride 가 X-Trans 패턴 주기(6px)와 같아 **같은 색 위치만** 뽑았다.
`(i*7)%f` / `(i*11)%f` 로 지터를 주고, 뽑힌 색 분포가 실제 CFA 비율과 정확히 같은지 확인했다.

### 스냅샷 식은 손으로 옮기지 않았다

`pipe` 블록의 바인딩에서 **생성**했다(스크립트). 54개를 손으로 옮기면 슬라이더 id 오타 하나가
uniform 하나를 조용히 0 으로 만들고, 그건 애니메이션에서만 드러난다. `pipeAnim` 의 133개
프로퍼티도 같은 이유로 `pipe` 텍스트에서 생성했다.
