# RAW Peek — 디모자이크 이전 센서 데이터 뷰 (`R`)

호기심 해소용 진단 뷰. 앱의 일반 경로는 `raw.postprocess()` 로 **디모자이크된 RGB** 만 다루는데
(`raw_loader._decode_native`), 이 뷰는 그 앞단 — 센서가 실제로 기록한 CFA 모자이크 자체 — 를 본다.
`docs/raw_demosaic.md`(디모자이크 정책)와 짝이다: 그쪽이 "무엇을 고를지"라면 이쪽은 "왜 그 선택이
차이를 만드는지"를 눈으로 보여준다.

구현 전까지 `raw.raw_image` / `raw_colors` / `black_level_per_channel` / `white_level` / `sizes` 를
읽는 코드가 **레포에 한 군데도 없었다**(`raw_pattern` 만 `_export_demosaic` 의 `.shape == (2,2)`
판별용). 전부 새로 뚫은 경로다.

## 왜 이 구조인가 — 렌더 경로 체크리스트를 원천적으로 안 건드린다

`CLAUDE.md` 의 **★ 렌더 경로**(프리뷰 `pipe` / GPU export `pipeFull` / CPU export
`pipeline.render_full` / 비교창 `comparePipe` 4중 배선)와 `LOOK_DEFAULTS` 44키, 사이드카·
export dict — **전부 무관**하다. 읽기 전용 진단 뷰라서 새 셰이더 uniform·새 룩 키가 **0개**다.
그 4중 배선 누락이 이 프로젝트에서 반복적으로 버그를 만들었으므로, 진단 기능은 그 표면에
아예 올리지 않는 것이 설계 목표였다.

- **셰이더를 쓰지 않는다.** 그림은 전부 `raw_peek.py` 가 numpy → QImage 로 그려 provider 로 넘긴다.
  ⚠️`adjust.frag` 는 D3D11 샘플러 16/16 을 이미 다 써서 샘플러를 늘리면 **파이프라인 생성에서
  죽는다**(qsb 컴파일은 통과한다).
- **디코드 경로 무변경.** `raw_loader.py` · `pipeline.py` · `wb.py` · `shaders/` 는 한 줄도 안 건드렸다
  (`raw_peek` 이 `wb.linear_to_srgb`/`srgb_to_linear`/`baked_wb` 를 **읽기만** 한다).

## 형태

`ui/PreviewWindow.qml` 과 같은 **인앱 전체화면 오버레이**(`Item { anchors.fill: parent; z: 1000 }`).
별도 OS 창이 아니라 메인 창 contentItem 을 덮으므로 씬그래프를 재사용하고 창 생성·포커스 비용이 없다.

`R` 로 열고 닫는다. **RAW 일 때만** 열린다(`controller.rawPeekAvailable` — 일반 이미지는 CFA 가 없다).

### 4개 모드 (`1`~`4`)

| 모드 | 보이는 것 |
|------|-----------|
| **Gray** | 모자이크를 그레이스케일로. 전체 보기에서는 모자이크가 평균화돼 그냥 흑백사진처럼 보이는 것 자체가 관찰 포인트 |
| **CFA** | 픽셀마다 자기 컬러필터 색으로 착색 + 반복 유닛 격자. **X-Trans 6×6 vs Bayer 2×2 차이가 드러나는 핵심 컷** |
| **Planes** | 색별 평면(해당 색만, 나머지는 검정) — 표본 밀도 비교. X-Trans G 55.6% / R·B 22.2%, Bayer 50/25/25 |
| **Demosaic** | 같은 크롭의 **모자이크 vs export 현상 결과** — X-Trans·Bayer 모두 `AHD` 하나. 제목은 실제 실행 알고리즘으로 표시(`_cand_label`: X-Trans 는 "Markesteijn 3-pass (AHD)") + `[app: export]`. 첫 렌더만 LibRaw 디코드(X-Trans 3.7s/Bayer 1.3s), 이후 수십 ms |

우측 패널: 패턴 유닛 차트 + **채널별 레인 히스토그램** + 메타 표.

### 미니맵 (확대 중 '지금 보는 곳')

8~32× 로 들어가면 전체 어디를 보는지 알 수 없어서 뷰 우하단에 미니맵을 둔다. 클릭·드래그로
그 위치로 점프한다.

- 미니맵 **이미지는 사진당 1회**만 만든다(팬/줌과 무관) → 오픈 시 워커에서 계산·캐시.
- 표시 사각형은 `controller.rawPeekRect`(= `raw_peek` 이 **실제로 자른** 센서 픽셀 x,y,w,h)에서
  나온다. ★QML 이 zoom·뷰 크기로 추정하면 **모드마다 틀린다** — Planes 는 폭을 색 수로 나누고,
  Demosaic 는 정사각 크롭이며, Boundary 는 크롭 개념이 없다. 그래서 렌더 함수가
  `st.last_rect` 에 실제 값을 남기고 그것을 보고한다.
- ⚠️비율대로만 그리면 **3~4px 점**이 된다(8× 크롭이 전체의 2%, 실측 137×114 / 6246×4170).
  → **최소 9px 박스 + 미니맵을 가로지르는 십자선**을 함께 그린다. 위치는 십자선이, 실제 크기는
  박스가 알려준다.
- 전체를 보고 있으면(크롭이 프레임의 95% 이상) 그리고 Boundary 모드에서는 숨긴다.
- ⚠️`rect` 가 빈 배열일 때 NaN 이 바인딩으로 새지 않게 `ok` 가드를 둔다.

## 설계 결정과 함정 (실측 기록)

### 채널 히스토그램은 반드시 레인 분리
채널을 겹쳐 그리면 `np.maximum` 블렌드로 색이 흰색·분홍·시안으로 섞여 **판독이 불가능**했다.
채널마다 자기 레인(lane)을 주고 x 축(0..white_level)만 공유한다.

### 감마는 확대 **전**에 적용
`_gamma8(_nearest_up(...))` 로 짜면 매 프레임 1600×1000×3 float 에 감마를 걸어 **62~146ms** 가
든다(7~16fps). nearest 확대는 값을 복제할 뿐이라 순서를 바꿔도 결과가 **수학적으로 동일**하고,
`_nearest_up(_gamma8(...))` 로 바꾸면 **22~100ms** 가 된다. 드래그 팬의 체감이 여기서 결정된다.

### CFA 패턴 격자는 QPainter 로 그리지 않는다
"CFA 만 드래그가 느리다(맥)" 는 보고로 재 봤다. 같은 사진·같은 뷰포트(1600×1000, 줌 2)에서
**Gray 8.5ms vs CFA 46.1ms** 였고, 그중 **20.9ms 가 패턴 유닛 격자**였다 — 선 218개를
`QPainter.drawLine` 으로 그린 값이다(픽셀당 ~90ns). **알파를 빼도(19.3ms), `drawLines` 로 묶어도
(20.6ms), ARGB32 로 포맷을 바꿔도(20.1ms) 같다** — 펜/포맷 문제가 아니라 래스터 경로가 느린 것이다.
numpy 로 행/열을 직접 블렌드하면 같은 그림이 ~2ms 다. **결과는 화소 단위로 동일**하다
(줌 2/4/8 전부 최대차 0코드) — 격자가 정수 좌표의 1px 수직/수평선이고 알파가 55/255 로 고정이라
반올림까지 맞는다. 적용 후 **CFA 47.7 → 29.8ms / 21.2 → 12.2 / 13.0 → 8.0**(줌 2/4/8).

⚠️격자는 **X-Trans 에서만** 그려진다(`period >= 3 && period*zoom >= 12`) — 베이어 파일로 재면
이 비용이 아예 없으니, 느리다는 보고를 받으면 **어떤 센서의 파일인지 먼저 확인할 것**.

남은 CFA 비용의 구조(줌 2, 크롭 800×500 기준): 감마 3채널 **10.4ms**(Gray 는 1채널 3.4ms) /
nearest 확대 3채널 **6.4ms**(Gray 는 1채널 0.7 + dstack 1.8) / 색 배열 만들기 4.5ms /
auto gain 2.4ms. **Gray 가 빠른 이유는 무거운 픽셀 연산을 흑백 1채널로 끝내고 맨 마지막에
`dstack` 으로만 3장을 만들기 때문**이고, CFA 는 색을 입힌 뒤라 감마·확대를 3채널로 통과시킨다.
⚠️감마를 색 입히기 앞으로 옮겨 1채널로 만들 수는 **없다** — `CFA_RGB` 가 순수 원색이 아니라
틴트라(R=(1.0,0.15,0.15)) 순서를 바꾸면 그림이 달라진다.

⚠️**이 구간은 플랫폼을 탄다.** 감마는 `x ** (1/2.4)` 인데 float32 pow 실측이 이 맥(arm64,
numpy 2.5.2)에서 **265 Mel/s**(1.2M 원소 4.6ms)다. x86-64 numpy 는 pow 에 SIMD(SVML) 경로가
붙어 보통 몇 배 빠르므로, 같은 코드가 윈도우에서 훨씬 가볍게 보일 수 있다. 4096칸 LUT 로 바꾸면
10.4 → 4.2ms 지만 **화소의 1.56% 가 1코드 달라져** 아직 적용하지 않았다.

### 캔버스 배경은 `canvas[:, :] = BG` 로 채우지 않는다
"Planes 도 맥에서만 느리다" 를 재 보니 **전체 19~26ms 중 7.1ms 가 배경 채우기 한 줄**이었다.
(H,W,3) uint8 에 3원소를 브로드캐스트하면 numpy 가 원소별 경로로 떨어진다 — 1580×998 에서
**6.9ms**(≈660MB/s). 한 줄 `(W,3)` 을 만들어 행 단위로 뿌리면 **0.11ms** 로 **62배**다
(`_bg_canvas`). 다른 방법들도 재 뒀다: 채널별 스칼라 대입 1.47ms(스트라이드 write 3회) /
`np.full` + 채널 보정 0.69ms / `reshape(-1,3)` 대입 7.10ms(같은 느린 경로).
같은 패턴이 **5곳**(라벨 밴드·Planes·Demosaic 비교·패턴 차트·히스토그램)에 있었다.
적용 후 **Planes 26.6 → 19.4ms(줌 2) / 14.3 → 7.8ms(줌 8)**, 픽셀은 전 모드·전 줌에서
이전 판과 **비트 동일**(패턴 차트·히스토그램 포함 실측).

### 확대는 Qt 에 맡긴다 (8배 줌 드래그가 끊기던 이유)

"CFA·Planes 에서 8배 확대 드래그가 자주 끊긴다" 는 보고. `zoom > 1` 은 **캐시 대상이 아니고**
(`is_heavy` 가 곧바로 False, 크롭이 매 이벤트 달라져 캐시가 성립하지도 않는다) **동기 렌더**라,
비용이 그대로 프레임에 실린다. 뷰포트 1700×950 실측(이벤트 1건):

| 모드 | z2 | z4 | z8 | z16 |
|---|---|---|---|---|
| Gray | 10.1ms | 4.9 | 3.4 | 3.0 |
| CFA | 30.3ms | 11.9 | 8.2 | 7.3 |
| Planes | 18.7ms | 10.1 | 7.8 | 7.5 |

★**z8 에서 비싼 것은 크롭이 아니라 '출력 크기로 키우는 것'이었다.** 분해(크롭 212×118 →
출력 1696×944): 크롭 정규화 0.04 / auto gain 0.17 / 색 입히기 0.24 / 감마 0.41 / **nearest 확대
5.91** / QImage 변환 0.39. Gray 가 싼 것은 1채널로 확대한 뒤 마지막에 `dstack` 하기 때문이다.

→ 확대를 `QImage.scaled(FastTransformation)` 로 옮겼다(`_up_qimage`/`_up_arr`). 같은 nearest 라
**결과가 비트 동일**하고(전 모드 × 줌 1/2/8/16 화소 비교) **6.58 → 1.07ms** 다. 적용 후:

| 모드 | z2 | z8 | z16 |
|---|---|---|---|
| Gray | 9.8 → 8.7ms | 3.4 → **1.5** | 2.9 → 1.1 |
| CFA | 28.0 → 23.1ms | 7.9 → **2.9** | 7.2 → 1.8 |
| Planes | 18.6 → 14.1ms | 7.5 → **3.0** | 7.4 → 2.5 |

⚠️**CFA 격자는 확대 뒤에 그려야 한다**(선이 1px). 그래서 확대된 QImage 버퍼에 numpy 뷰
(`_qview`)로 블렌드한다. ⚠️`_qview` 결과를 **QImage 보다 오래 들고 있지 말 것** — 해제된 버퍼를
가리킨다. 캔버스에 붙이는 경로(디모자이크 패널)는 `_up_arr` 가 복사본을 준다.

★⚠️**그 복사는 `np.array(..., copy=True)` 여야 한다 — `np.ascontiguousarray` 는 복사하지 않는다.**
뷰가 이미 연속이면 그대로 돌려주는데, `scaled()` 결과는 `bytesPerLine == w*3` 이라 **항상**
그 경우다(폭 100/101/102/211/212 전부 확인). 그렇게 두면 QImage 가 함수에서 나가며 해제돼
배열이 해제된 버퍼를 가리키고, **디모자이크 패널이 간헐적으로 깨진다**(사용자 보고로 잡았다 —
"demosaic 에서 CFA 화면이 깨질 때가 많고 불안정"). 고친 뒤 메모리 교란을 사이에 두고 같은
요청을 3회 재렌더해 전부 비트 동일함을 확인했다.
⚠️z2 는 개선폭이 작다(크롭이 커서 감마·색 입히기가 지배한다) — 거기서 더 줄이려면 감마 LUT다.

### 드래그는 프레임당 1회로 묶는다
`onPositionChanged` 가 곧바로 `refresh()` 를 부르면 **마우스 이동 1건마다** 동기 렌더 +
텍스처 업로드가 GUI 스레드에서 돈다(이동은 초당 60~120건). `refreshSoon()` 이 `Qt.callLater`
로 한 턴에 하나만 남긴다. ⚠️모드·줌 전환 같은 **단발** 이벤트는 그대로 `refresh()` — 묶으면
반응이 한 턴 늦어 보인다.

### 무거운 것만 워커, 가벼운 것은 동기
| 작업 | 실측(X100V 26MP) | 처리 |
|------|-----------------|------|
| `rawpy.imread` + 배열 복사 | 0.62s | 오픈 시 워커 1회 |
| 히스토그램 | 0.80s | 오픈 시 워커 1회, 캐시 |
| 패턴 차트 | 0.02s | 오픈 시 워커 1회, 캐시 |
| 모자이크 zoom≥2 | 22~100ms | **동기** — 드래그가 즉시 따라온다 |
| 모자이크 zoom=1(전체) | 0.25~0.38s | 워커 + `(mode,w,h)` 캐시 |
| Boundary | 35~63ms | 동기 |
| Demosaic 후보 비교 (첫 호출/창 미스) | 13.7s(X-Trans) / 5.7s(Bayer), 4종 디코드 | 워커 + 진행 표시 |
| Demosaic 후보 비교 (창 히트) | **6~14ms** | 동기 |

무거운 요청은 **코얼레싱**한다(`_stamp_worker` 와 같은 패턴) — 드래그마다 스레드를 띄우면 요청이
쌓여 오히려 늦는다.

### ★Demosaic 패널은 무엇을 위한 것인가 — 정책 검증 계측기

이 레포엔 `docs/raw_demosaic.md` 라는 **결정 기록**이 있다: 프록시는 항상 LINEAR, export 는
AHD(2026-08-29 부터 X-Trans 도 — LibRaw 에선 Markesteijn 3-pass. 그 전엔 Bayer 만 AHD 였다).
그 결정은 논거로 내려졌고 "알려진 트레이드오프(수용됨)" 와
**"추후 재검토 트리거"**(더 나은 알고리즘 DCB/DHT 검토 시)까지 적혀 있는데, 그걸 **내 사진에서
재볼 수단이 앱에 없었다.** 이 패널이 그 계측기다.

★**후보 디코드는 export 계약과 동일하다**(2026-08-29, `_dm_get`): TREF WB(baked_wb)+감마
(2.4, 12.92), 유일한 차이는 `user_flip=0`(크롭 창의 센서 좌표 정합 — 회전만 다르고 픽셀 동일).
예전엔 유니티 WB+선형으로 디코드했는데 두 가지가 틀렸다: ①WB 는 디모자이크 **전에** 곱해져
(LibRaw scale_colors) 패널이 export 와 **다른 디모자이크**를 보여줬고, ②초록 캐스트+선형+p99
상시 게인이 평탄부 노이즈 결(Markesteijn 의 지렁이 결)을 과장해 올바른 정책을 의심하게 만들었다
(`docs/raw_demosaic.md` 전환 기록). 후보 패널의 표시 게인도 이제 Display gain 토글을 따른다
(켜면 `_auto_gain` — 첫 후보에서 1회 산출해 **후보 간 동일 게인**, 끄면 export 디코드 그대로).
CFA mosaic(입력) 패널은 지금도 as-recorded 다(센서 데이터를 보여주는 게 RAW Peek 의 정체성).

패널: `입력 모자이크` + `LINEAR` + `AHD` + `DCB` + `DHT`. 앱이 실제로 쓰는 것에는
`[app: proxy]` / `[app: export]` / `[app: proxy+export]` 표시가 붙어, "지금 정책이 이 사진에서
타당한가" 를 바로 볼 수 있다.

**★기각한 이전 설계**: 두 번째 패널이 `naive box fill`(마스크된 균등 평균) 이었다. **어떤 결정에도
기여하지 않는다** — 파이프라인 후보가 아니고, 실측 집계도 LINEAR 와 거의 같았다(선명도 0.0306 vs
0.0326, 표본지점 편차 R 0% G 7% B 0%). "왜 이걸 비교해 보여주나"에 답이 없어 제거했다.
그 측정 과정에서 X-Trans 창을 5x5 로 뒀던 근거가 **가정이었고 측정에 반박당한** 것도 나왔다 —
3x3 안에 모든 색이 최소 1개 있다(Bayer R/G/B/G2 각 1, X-Trans R=1 G=5 B=1).

**⚠️"같다/다르다"는 차이의 크기까지 재야 한다 (두 번 틀린 자리)**

1. LINEAR 과의 평균 절대차가 AHD/AAHD/DCB/DHT 에서 **142.62 로 똑같이** 나와 "넷은 같은 경로"라고
   결론지을 뻔했다 → `array_equal` 로 보니 전부 False 여서 "전부 다르다"고 **정정했는데 그것도
   틀렸다.**
2. 차이의 **크기**를 재니: X-Trans 에서 AHD vs DCB 는 다른 픽셀 **0.04%**, 평균 절대차 **0.03
   코드**(16bit). DCB vs DHT 도 0.06% / 0.05 코드. **실질 동일**이고 4파일 x 4크롭 품질 지표가
   소수 5자리까지 같았다. `array_equal` 의 False 는 반올림 수준이었다.
   (2026-08-29 확인: X-Trans 의 quality>2 는 **전부 같은 Markesteijn 3-pass**고, 그 미세차의
   정체는 **실행 간 비결정 지터**였다 — 같은 라벨로 두 번 디코드해도 0.003~0.02% 픽셀이 다르다.
   `docs/raw_demosaic.md` 매핑 절 참조.)

→ 그래서 후보 집합을 **CFA 종류별**로 둔다(`demosaic_candidates`). X-Trans 에서 실제로 갈리는
것은 **LINEAR / VNG / PPG(=Markesteijn 1-pass) / AHD 계열(=Markesteijn 3-pass)** 이다
(Mark1 vs Mark3 는 다른 픽셀 21.7%, 평균 17.3 코드로 진짜 다르다). 넷을 AHD·DCB·DHT 로
채우면 **똑같은 패널 3장에 ~10s** 를 쓰게 된다.
Bayer 는 LINEAR/AHD/DCB/DHT 가 서로 뚜렷히 다르다(LINEAR 대비 평균차 95/79/88).

### 후보를 LINEAR 하나로 줄인 결정 (사용자)

4종 비교는 X-Trans 첫 렌더가 **13s** 였고(종당 1.1~3.6s), 아래 벤치마크에도 불구하고
**눈으로는 판별이 안 됐다**("내눈엔 잘 모르겠다"). 비용 대비 얻는 게 없어 `LINEAR` 하나로
줄였다 → 첫 렌더 **1.11s**(X-Trans) / 0.73s(Bayer), 캐시 101MB → **25MB**, 패널이 2장이라
훨씬 크게 보인다(1400x716 vs 1398x292).

남긴 기준은 **export 가 실제로 쓰는 것**이다(`raw_loader._export_demosaic` 과 짝).
2026-08-29 X-Trans export 가 AHD(=Markesteijn 3-pass)로 전환되며 잠시 X-Trans 후보를
`LINEAR+AHD` 둘로 늘렸다가, **같은 날 사용자 결정으로 LINEAR(프록시용)를 양쪽 모두 뺐다** —
프록시는 2560 축소라 이 100% 비교와 체감이 무관하고, 빼면 첫 렌더가 빨라지고 패널이 커진다
(크롭 131→198px):

| | 후보 | 패널 | 첫 렌더 |
|---|---|---|---|
| X-Trans | `AHD`(export — Markesteijn 3-pass) | 2 | 3.7s |
| Bayer | `AHD`(export) | 2 | 1.3s |

- 패널은 **모자이크(입력) vs export 결과** 전후 비교다 — 100% 화질이 의미 있는 곳은 export
  뿐이라는 `docs/raw_demosaic.md` 의 논거와 같은 기준.
- 후보를 늘릴 때는 `_CANDS_XTRANS` / `_CANDS_BAYER` 두 줄이다. 아래 벤치마크 표를 먼저 볼 것.

### ★후보 디코드는 창(window) 단위로 캐시한다

LibRaw 는 전체 프레임만 디코드할 수 있고 그게 비용의 거의 전부다(종당 실측):

| | LINEAR | AHD | DCB | DHT | 합 |
|---|---|---|---|---|---|
| X-Trans 26MP | 1.11s | 3.60s | 3.55s | 3.52s | **13.7s** |
| Bayer 12MP | 0.71s | 0.91s | 2.88s | 0.85s | **5.7s** |

전체 프레임을 4종 보관하면 26MP 에서 624MB 다. → **`DM_WINDOW`(2048px) 창만 잘라 보관**한다:
종당 25MB, 4종 **100.7MB**(실측). 크롭이 최대 ~250px 이라 ±900px 팬까지 미스가 없다.

| | 시간 |
|---|---|
| 첫 렌더(4종 디코드) | 13.7s / 5.7s |
| 줌 변경(캐시 히트) | **6.2~14.1ms** |
| 창 안 팬 | **7ms** |
| 창 밖 팬(미스 → 재디코드) | 13.8s / 5.7s |

- `is_heavy()` 가 `demosaic_cached(st, demosaic_crop(...))` 로 판정해 **창 미스면 워커**,
  히트면 **동기**로 간다. ⚠️그래서 `is_heavy` 가 `cx/cy` 를 받아야 한다 — 없으면 팬 미스를 못 본다.
- 첫 렌더가 길어 침묵하면 멈춘 것처럼 보이므로 후보별 진행을 알린다
  (`progress` 콜백 → `rawPeekStatus` → 뷰 우상단 배지 "decoding AHD (2/4)…").
- ★`_demosaic_slot`/`_demosaic_side_k` 를 `demosaic_steps`·`zoom_range`·`demosaic_crop` 이
  **공유**해야 UI 줌 상한과 캐시 히트 판정이 실제 렌더와 어긋나지 않는다.

### 오픈 시 기본 팬 위치는 '디테일 있는 중간톤'

화면 중앙은 하늘·벽 같은 평탄면일 때가 많고, 그러면 **후보 4개가 똑같아 보여 비교가 무의미**해진다.
`default_center()` 가 축소본에서 블록별로 `표시공간 표준편차 x 중간톤 가중 x 클립 페널티` 를 매겨
가장 좋은 지점을 고른다(가장자리 15% 는 크롭이 잘려 제외).

실측(같은 크기 크롭의 표준편차 = 디테일): X-Trans 0.1599 vs 중앙 0.0407(**x3.9**) ·
Bayer 0.0989 vs 0.0632(x1.6) · 폰 DNG 0.1149 vs 0.0974(x1.2) · DJI 0.2164 vs 0.0292(**x7.4**).
비용 0.45~1.2s 이고 로드 워커에서 한 번만 돈다(추가 디코드 없음 — 정규화 배열 재계산뿐).

### ★Demosaic 패널 크기는 줌과 무관하게 고정 — 슬롯을 먼저 정한다

줌은 **"얼마나 확대해 보는가"(=크롭이 얼마나 작아지는가)** 만 바꿔야 하고 패널의 화면 크기는
그대로여야 한다. 처음엔 패널 크기를 `크롭 x 줌` 에서 파생시켰는데 그래서:

- 정수 나눗셈으로 줌마다 폭이 미세하게 흔들렸다(1098 → 1092 → 1080).
- 고배율에서 크롭이 하한(패턴 4주기)에 걸리면 `side*zoom` 이 슬롯을 넘어, "안 맞으면 줌을
  절반씩 낮춘다"는 폴백이 발동해 **이미지가 1080 → 600px 로 쪼그라들고 줌 16·32 가 똑같이
  8로 렌더**됐다(사용자 보고).

→ **슬롯(`slot`, 정사각 칸)을 먼저 고정하고 패널을 그 안에 가운데 정렬로 넣는다**(`_slots`).
총 크기 = `slot×n + gap×(n−1)` 이라 줌과 무관하게 일정하다(실측 distinct sizes = 1).

- 확대율은 `k = min(요청, slot // side)` — 요청 배율이 들어가면 **그대로** 쓴다.
  ⚠️`min` 없이 `slot // side` 만 쓰면 크롭 하한에 걸린 Bayer 32× 가 **33×** 로 넘어갔다.
- 크롭 하한에 걸려 요청 배율을 못 맞추면 **캡션에 적는다** — 조용히 다른 배율로 그리지 않는다.

### 크롭은 파이썬에서 자른다

26MP 를 32× 로 올린 텍스처는 존재할 수 없다. `mosaic()` 이 요청된 center/zoom·뷰포트 크기로
**화면에 들어갈 픽셀만** 잘라 nearest 확대한다. QML 은 스케일하지 않는다(`fillMode: Image.Pad`).
크롭 크기는 `ceil` 이 아니라 **내림** — `ceil` 이면 `cw*zoom` 이 요청 폭을 넘는다(1608 > 1600).

Planes 는 색당 패널 1장을 가로로 늘어놓으므로 **크롭 폭을 색 수로 나눠야** 뷰포트에 들어간다
(안 나누면 3~4배 넓은 그림이 나와 화면 밖으로 밀린다). 패널 제목줄 높이도 예산에서 뺀다.

### ★캡션은 이미지에 굽지 않는다 — QML 이 고정 높이 밴드에 그린다

같은 자리를 **세 번** 고친 뒤 구조를 바꿨다. 굽던 시절의 실패 사슬:

1. 라벨이 이미지보다 넓으면 **캔버스를 넓혔다** → 뷰가 `fillMode: Pad` + `centerIn` 이라
   뷰포트보다 넓은 캔버스는 **가운데만 보인다.** 라벨이 양쪽으로 잘리고 모자이크도 어긋나
   "모드를 바꿔도 안 바뀌는 것처럼" 보였다(실측: 요청 1600px 에 CFA **1940px**).
2. 그래서 접도록(`_wrap`) 바꿨더니 이번엔 **높이**가 넘쳤다 — 크롭 높이를 `out_h` 로 잡고
   그 위에 밴드를 더하는 구조라 총 높이가 **항상** 뷰포트를 초과했다("확대되면 상단 텍스트 잘림").
3. 밴드 높이를 미리 빼려 했지만 **줄바꿈 여부를 알 수 없어** 좁은 폭에서 또 넘쳤다
   (예산 83px vs 실제 117px — 판정문이 2줄로 접혔다).

→ **메인 뷰(`mosaic`/`boundary`/`demosaic_steps`)는 `(QImage, [캡션줄])` 을 돌려준다.**
QML 이 `topBar` 아래 **고정 높이 40px** 밴드에 그리고, 이미지 영역(`view`)은 그 아래에 앵커된다.
이러면 이미지 높이 예산이 정확해지고(요청 = 실제 가용 픽셀) 캡션은 절대 잘리지 않는다.

- ⚠️캡션 밴드 높이는 **고정**이어야 한다. 내용에 따라 높이가 변하면 `view.height` 가 바뀌고
  그게 재렌더를 유발해 진동한다.
- 캡션은 **짧게**(1~2줄) 유지한다. 상세 수치는 어차피 우측 정보 패널(`rawPeekInfo`)에 있다.
- `pattern_chart`/`histogram` 은 폭이 고정된 패널 도판이라 `_label_band` 로 계속 굽는다.
- 정보 패널 폭은 `min(500, 창폭×0.34)` — 1280 창에서 뷰가 780px 로 쪼그라들지 않게.
- QML `view` 에 `clip: true`(안전망).

### ★모드 디스패치는 `raw_peek.render` 하나뿐이다

동기 경로(`Controller.rawPeekView`)와 워커 경로가 **각자 모드 분기를 적고** 있었다. 평소엔
Demosaic 이 항상 워커로 가서 문제가 없었는데, 캐싱을 넣어 `is_heavy` 가 False 를 돌려주는 순간
**동기 쪽에 `MODE_DEMOSAIC` 분기가 없어** `mosaic()` 으로 떨어졌다 → mode 3 이 `_render` 의 CFA
분기로 흘러 **패널 하나만 CFA 처럼** 나왔다(사용자 보고: "드래그시 CFA 모드처럼 하나만 나오네").

→ 디스패치를 `raw_peek.render()` 하나로 합쳤고, 두 경로 모두 그것만 부른다.

★**검증은 픽셀을 비교해야 한다.** URL 이 바뀌는지·시간이 짧은지만 보는 검사는 이 버그를
**통과시킨다**(실제로 통과했다). `dispatch_test` 는 Controller 산출물과 `raw_peek.render` 결과를
모드별로 비트 비교하고, Demosaic 은 **cold(워커)/warm(동기) 두 경로를 모두** 태운다.

### ⚠️드래그 환산은 `zoom` 이 아니라 실제 배율(`rawPeekScale`)로

`zoom` 으로 환산하면 Demosaic 에서 드래그가 n 배 느려진다 — 패널이 화면의 1/n 이고, 고배율에서는
크롭 하한 때문에 캡도 걸린다(실측 zoom 32 → 실제 14×). 그려질 때마다 `st.last_scale`(표시 픽셀 /
센서 픽셀)을 남기고 QML 이 그걸 쓴다. 전체 보기는 축소라 1 미만(0.167)이다.

Demosaic 도 크롭이 있으므로 **드래그가 된다**(예전엔 `isMosaic` 게이트로 막혀 있었다).
Boundary 만 visible 안의 위치라는 개념이 없어 제외한다.

### ★줌 범위는 모드·뷰포트마다 다르다 — UI 가 1..32 를 그대로 쓰면 안 된다

`raw_peek.zoom_range(st, mode, w, h)` 가 **실제로 서로 다른 결과가 나오는** 범위를 돌려주고
QML `setZoom()` 이 휠·`+`/`−`·버튼을 그 안으로 클램프한다. 안 하면 사용자 보고처럼 된다:

> `2x(패닝안됨) -> 2x(패닝 됨) -> ... -> 14x -> 14x (14x가 반복됨)`

두 원인이 겹쳐 있었다.

1. **Demosaic 은 내부에서 `clip(zoom, 2, 32)`** 로 올려 잡으므로 `zoom` 1 과 2 가 **같은 그림**인데,
   `canPan` 이 `zoom > 1` 을 보고 있어 앞쪽만 패닝이 막혔다 → "2x 인데 안 움직이는" 상태가 하나 더.
   → `canPan` 을 **"지금 그려진 것이 실제 크롭인가"**(`rect` 가 프레임보다 작은가)로 바꿨다.
   모드·zoom 과 무관하게 옳고, 전체 보기에서는 자동으로 꺼진다.
2. **크롭 하한** 때문에 X-Trans 는 16x·32x 가 둘 다 14x 로 그려져 휠 두 칸이 무동작이었다.
   → `zoom_range` 가 배율이 더 안 올라가는 지점을 상한으로 잡는다(k 가 같아지면 중단).

실측 줌 계단(모두 서로 다른 배율/크롭):

| | 범위 | 계단 |
|---|---|---|
| X-Trans Demosaic @1100×860 | 2..16 | 2x/179px · 4x/89 · 8x/44 · 14x/24 |
| X-Trans Demosaic @1500×900 | 2..32 | 2x/246 · 4x/123 · 8x/61 · 16x/30 · 20x/24 |
| Bayer Demosaic @1100×860 | 2..32 | 2x/133 · 4x/66 · 8x/33 · 16x/16 · 32x/8 |
| 모자이크 모드 | 1..32 | 1 = 전체 보기(패닝 꺼짐) |

- 상단 줌 표시는 **요청값이 아니라 실제 배율**(`rawPeekScale`)이다 — Demosaic 은 다를 수 있다.
- Boundary 는 `zoom_range` 가 (1,1) 이고 `+`/`−`·줌 표시가 숨는다.
- ⚠️`_demosaic_slot`/`_demosaic_side_k` 를 `demosaic_steps` 와 `zoom_range` 가 **공유**해야
  UI 상한이 실제와 맞는다. 따로 적으면 다시 무동작 칸이 생긴다.

### ⚠️휠 줌을 `MouseArea.enabled` 로 막으면 다시 확대할 수 없다

드래그 팬을 `enabled: isMosaic && zoom > 1` 로 게이팅했는데, `onWheel` 이 **같은 MouseArea 안**에
있어서 줌이 1이 되는 순간 영역이 비활성화되고 **휠 이벤트가 아예 오지 않았다**
(사용자 보고: "scale down 은 되는데 scale up 안 됨"). → MouseArea 는 항상 켜 두고 **드래그만
핸들러 안에서** 게이팅한다(`canPan`).

### ⚠️드래그 깜빡임 = `asynchronous: true`

provider 가 그림을 교체할 때마다 `Image` 가 Loading 상태로 가며 **이전 픽스맵을 버려** 빈 프레임이
낀다. provider 는 이미 메모리에 있는 QImage 를 돌려주므로(수 MB memcpy) `asynchronous: false` 가
맞다.

### ★⚠️알림(`rawPeekChanged`)은 **다음 이벤트 루프 턴으로 미뤄야 한다**

동기 렌더 경로는 QML 의 `onModeChanged` / `onRawPeekChanged` 핸들러 **안에서** 파이썬까지
들어온다. 그 상태로 `rawPeekChanged` 를 그대로 발화하면 **재진입**이라 QML 이 바인딩을
재평가하지 않는다. 증상은 **"버튼은 반응하는데 화면이 안 바뀐다"** — 사용자 보고 그대로다.

실측(고치기 전): `controller.rawPeekUrl` 은 113 → 114 → 115 → 116 으로 올라가는데
`Image.source` 는 `?v=112` 에 **멈춰 있었다**(`sourceSize` 도 안 바뀜). 게다가 재진입이
피드백 루프를 만들어 첫 렌더까지 **publish 가 113번** 돌았다.

`QTimer.singleShot(0, self.rawPeekChanged.emit)` 로 한 턴 미루면 `Image.source` 가 URL 을
정확히 따라가고(v=2→3→4→5, `sourceSize` 도 모드별로 바뀜) publish 는 상호작용당 **정확히 1번**이
된다. 사람이 느낄 지연은 없다.

★**검증은 `controller.rawPeekUrl` 이 바뀌는 것까지 보면 안 된다** — 그건 고치기 전에도 통과했다.
`Image` 아이템의 `source`/`sourceSize` 를 실제로 읽어야 이 버그가 잡힌다(`objectName:
"rawPeekImage"` 를 그래서 달아 뒀다).

### ⚠️`QT_QPA_PLATFORM=offscreen` 에서는 라벨이 전부 두부(tofu)
offscreen QPA 는 `QFontDatabase.families()` 가 **0개**다(native `windows` 는 390개). 에러도 안 나고
PNG 도 정상 생성되므로 **그림을 열어볼 때까지 모른다.** 앱 본체는 native 라 문제없지만, 이 모듈의
그림을 헤드리스로 뽑는 검증 스크립트에서는 offscreen 을 쓰지 말 것(창을 안 띄우면 native 로도
헤드리스로 돈다). QML 로드/경고 검사에는 offscreen 이 계속 옳다.

### 창 단위 `Shortcut` 은 오버레이가 떠 있어도 발화한다
전체화면 오버레이 뒤에서 `Ctrl+Z`(undo)·`D`(스탬프 토글 + 내 기본값 기억) 같은 **실제 부작용이
있는** 단축키가 눌릴 수 있다. `ui/Main.qml` 에 `_keysBlocked = _typing || rawPeekWin.visible` 를
두고 기존 가드를 전부 그쪽으로 승격했다.
★**새 단축키를 추가할 때는 `!win._typing` 이 아니라 `!win._keysBlocked` 를 쓸 것.**

## 마진 판정 (우측 정보 패널) — 두 가지를 **따로** 본다

⚠️예전엔 `Boundary` 라는 **모드**로 visible↔마스크 경계를 1:1 로 그렸다. 사용자 결정으로
그 모드는 제거했고(`docs/raw_demosaic.md` 정책 검증이 눈으로 판별되지 않았다), 아래 **측정
내용은 `summary()` 가 정보 패널 텍스트로 계속 넣는다** — 정보는 남고 모드만 없어졌다.

`margins()` 는 마스크 마진의 성격을 두 축으로 판정한다. 처음에 하나로 묶었더니 D90 이
**오답**(평평한 광학 블랙인데 "광학 블랙 아님")으로 나왔다.

- `flat` : 0 패딩이 거의 없고 sd 가 작다 → 덮인 픽셀(읽기 노이즈만)
- `agrees` : 그 평균이 메타의 `black_level_per_channel` 과 맞는다

실측(제조사마다 완전히 다르다):

| 파일 | 마진 | 실측 | 판정 |
|---|---|---|---|
| X100V RAF | 우 138×4170 | **95.7% 가 정확히 0** | 광학 블랙 아님 — 단순 패딩 |
| Nikon D90 | 우 42×2868 | zeros 0%, mean 255.3, sd **1.31** | 광학 블랙이지만 pedestal(255)이 `black_level=0` 과 불일치 |
| LG Nexus 5X | 좌 48×3024 | mean 47.8, sd 10.1 (`black_level` 52) | 광학 블랙, 메타와 일치 |

⚠️**D90 의 불일치는 원인 미조사다.** 덮인 픽셀이 255 로 평평한데 LibRaw 는
`black_level_per_channel=[0,0,0,0]` 이라 보고하고, visible 영역에는 255 보다 낮은 값(최소 6)도
있다. NEF 압축/선형화 커브 쪽으로 보이지만 확인하지 않았다 — **마스크 스트립을 실제로 쓸 일이
생길 때** 파볼 값어치가 있다.

## 표시 규약

- 정규화: `v = (raw − black[c]) / (white − black)` — 채널별 블랙 차감.
- 표시 게인: raw 는 scene-linear 라 그냥 그리면 어둡다 → p99 기준 자동 게인(앱 자동노출과 같은 취지).
- 감마: `wb.linear_to_srgb`(셰이더·`raw_loader` 와 같은 함수) 재사용.
- ⚠️`camera_whitebalance` 의 **스케일은 파일마다 다르다**(Nikon 475/256/319 vs DNG 1.78/1.0/1.72)
  → 정보 패널은 G=1 로 정규화해 보여준다. 안 그러면 파일 간 비교가 안 된다.
- ⚠️`raw_colors_visible` 은 X-Trans 에서 `{0,1,2}`, Bayer 에서 `{0,1,2,3}`(G2 별도) 로 나온다.
  코드가 3색/4색을 모두 다루고, G2 는 그릴 때 G 와 합치되 통계는 분리한다.

## 메모리

오픈 시 `raw_image`(uint16) + `raw_colors`(uint8) 를 보관한다 — 26MP 기준 **53MB + 26MB**.
`rawPeekClose()` 가 참조를 버리고 provider 를 비운다.

## 표시 게인 토글 (`Display gain`)

Gray/CFA/Planes/Demosaic 그림은 `_auto_gain`(선형 p99 를 0.85 로 올리는 값)으로 밝기를
끌어올려 왔다. 센서값을 눈으로 확인하는 것이 이 탭들의 목적이라 그게 맞았지만, 그 값이
**실측 5~15배**라 "센서가 실제로 이만큼 적었다" 를 보여주지는 못한다.

상단 바에 체크박스를 뒀다. 끄면 게인 없이 `norm`(센서값을 포화로 정규화한 값) 그대로다 —
Develop 탭 머리 그림과 **같은 상태**다.

실측(DSCF2354, 8× 크롭 · 평균 코드):

| 탭 | 켜짐 | 꺼짐 | 캡션 |
|---|---|---|---|
| Gray | 128.3 | 56.8 | `display gain x5.3` / `display gain off (as recorded)` |
| CFA | 83.4 | 35.7 | 같음 |
| Planes | 26.9 | 11.8 | `x5.7` / off |
| Demosaic | 145.1 | 103.0 | `x14.9` / off |

- 기본은 **켜짐**(기존 동작).
- Develop 탭도 **같은 체크박스를 따른다**(사용자 요청). 머리 프레임(Gray/CFA 모자이크)에
  게인이 곱해진다. ⚠️켜면 머리가 밝아지는 대신 **셰이더 t=0 과의 이음새가 벌어진다**
  (실측 DSCF2354: 평균 2.7코드 -> 48.8코드). 이음새를 재는 검증은 반드시 **끈 상태**로.
  실측 머리 평균: 게인 끄면 gray 20.5 / cfa 14.5(셰이더 t=0 예상 17.8), 켜면 68.0 / 36.7.
- ⚠️`mosaic()` 의 전체보기 캐시 키(`(mode, out_w, out_h)`)에 **플래그를 넣어야 한다.**
  안 넣으면 토글해도 캐시된 그림이 그대로 온다.
- ⚠️**`@Slot` 서명이 QML 이 넘길 수 있는 인자를 정한다.** `rawPeekView` 의 파이썬 쪽에만
  인자를 더했더니 QML 의 7번째 인자가 조용히 버려져 **체크박스를 눌러도 아무 일이 없었다**
  (캡션까지 그대로라 금방 드러났다). `@Slot(int, float, float, int, int, int, bool)` 로 고쳤다.
- ⚠️`ui/RawPeekWindow.qml` 은 Controls 를 **`as B` 로 별칭 임포트**한다 — 무한정 `ToolTip`
  첨부 객체가 없어서 `ToolTip.visible` 을 쓰면 "Non-existent attached object" 로 **QML 로드가
  통째로 실패**한다. `B.ToolTip.visible` 로 쓸 것.
